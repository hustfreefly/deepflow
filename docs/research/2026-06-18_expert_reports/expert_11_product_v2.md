> **评估对象**: DeepFlow 架构重设计 V2 修正方案  
> **核心视角**: 忠礼作为用户的决策流程、心智模型、决策疲劳控制

## 一、研究输入摘要

### 1.1 Human-in-the-Loop Checkpoint 设计原则

**核心结论**（综合 Zapier / Databricks / Agno 等多方最佳实践）：

| 原则 | 说明 |
|------|------|
| **高风险决策点** | 不可逆操作、重大资源消耗前必须有人工检查点 |
| **低置信度暂停** | AI 输出置信度低于阈值时，自动暂停等待人工 |
| **选择性 HITL** | 不是每个步骤都需要人工——只在"关键时刻"（moments that matter）插入 |
| **Inline vs Selective** | 高风险环境用 Inline（每步都审），一般场景用 Selective（只审异常） |
| **Chain 边界检查** | 多步管线在阶段边界设置检查点，防止错误级联 |

**对 DeepFlow 的启示**：忠礼的工作流有 5 个潜在阶段（想法→方案→拆解→执行→结果），但不是每个阶段都需要忠礼介入。

### 1.2 Progressive Disclosure 设计策略

**核心结论**（综合 UX Planet / MindStudio / Smart Interface Patterns）：

- **分层展示**：先给摘要层（全局概览），再给详情层（按需展开）
- **用户控制权**：让用户决定深入程度，不要一次性倾倒所有信息
- **可纠正/可覆盖**：所有 AI 输出都应该是可编辑、可撤销、可覆盖的
- **结构化输出**：对开发者而言，把 AI 输出当 API 设计（有 schema），减少 UI 猜测

**对 DeepFlow 的启示**：Ship Package 对忠礼来说不是需要逐字段审查的 artifact，而是一个"摘要→详情"的分层展示对象。

### 1.3 GitHub Copilot Workspace 的 Plan → Code 过渡

**核心流程**：
```
Task → Spec → Plan → Code → Review/Test → PR
         ↑         ↑                        ↑
      自动生成   人工确认点               人工审查点
```

**关键设计决策**：
- **Plan 阶段是核心确认点**——开发者在此审批/编辑/拒绝每个步骤
- **Code 阶段是自动的**——一旦 Plan 确认，代码生成不需要逐步确认
- **所有输出完全可编辑**——从 Plan 到 Code，开发者随时可以修改
- **Coding Agent（异步模式）**：分配 Issue → 自动创建环境 → 自动编码 → 生成 Draft PR → 开发者审查

**对 DeepFlow 的启示**：Copilot 的经验证明——**Plan 确认是唯一的必要人工检查点**。Task breakdown 和 Code generation 之间不需要额外的人工步骤。

### 1.4 用户决策疲劳研究

**核心结论**：

| 策略 | 说明 |
|------|------|
| **自动化常规验证** | 后台自动处理身份验证、合规检查等，减少重复性微决策 |
| **智能默认值** | 不展示所有选项，只推荐 1-2 个最优方案 |
| **上下文感知优先级** | 只展示与当前决策直接相关的信息 |
| **过滤与洞察** | 过滤掉不满足标准的选项，只呈现精炼后的选择 |

**警示**：过度依赖 AI 会导致"AI brain fry"——用户需要持续高强度监督 AI 工具时产生的精神疲劳。**DeepFlow 必须避免让忠礼陷入"持续监督 AI 输出"的状态。**

## 二、忠礼的实际工作流分析

### 2.1 当前心智模型

```
忠礼的想法
    ↓
"我要做一个 XX 系统"
    ↓
Solution Pro 出方案（~30分钟）
    ↓
忠礼看方案 → 确认/修改 ← 【决策点 1：方案确认】
    ↓
（中间过程：Ship Pro 拆解 → Super Loop 编码）
    ↓
忠礼看最终结果 ← 【决策点 2：结果验收】
```

**忠礼关心的只有两件事**：
1. **方案对不对**（方向性判断）
2. **结果好不好**（质量判断）

中间的"怎么拆解任务"、"怎么分配工时"、"代码怎么写"——这些是**执行细节**，忠礼不想也不需要逐步确认。

### 2.2 忠礼的角色定位

忠礼是**产品决策者**，不是技术执行者。他的价值在于：
- 判断需求是否合理
- 判断方案方向是否正确
- 验收最终交付物是否满足需求

他**不应该**花时间审查：
- Work Package 的技术细节
- 工时估算是否合理
- 依赖关系图是否正确
- 集成检查点是否完整

## 三、对核心问题的逐一回答

### Q1: 忠礼需要看到几个"决策点"？

**建议：2 个决策点，不多不少。**

| 决策点 | 内容 | 性质 | 为什么必须 |
|--------|------|------|-----------|
| **DP-1: 方案确认** | final_result 的核心架构 + 关键设计决策 | 方向性判断 | 方向错了，后面全白做 |
| **DP-2: 结果验收** | 最终交付物 + RTM 需求覆盖 | 质量判断 | 确认交付满足需求 |

**不应该有的决策点**：
- ❌ 任务拆解确认（Ship Package 审查）——这是执行细节，忠礼不关心
- ❌ 工时估算确认——这是 AI 的专业判断，忠礼没有信息来验证
- ❌ 依赖关系确认——这是技术细节
- ❌ 每个 WP 的 AC 确认——太多了，会导致决策疲劳

**实施信心：9/10**

> 理由：Copilot Workspace 验证了"Plan 确认是唯一的必要人工检查点"。DeepFlow 多一个"结果验收"是合理的（因为 DeepFlow 的输出不是代码 PR，忠礼需要确认最终交付物）。

---

### Q2: Ship Package 是忠礼需要确认的 artifact 吗？

**建议：不是。Ship Package 应该完全自动化。**

**理由**：

1. **Ship Package 不是可操作的 artifact**
   - 里面有 WP 的技术细节、工时估算、依赖关系——忠礼无法基于这些信息做出有价值的判断
   - 如果忠礼看到"WP-003 需要 40 小时"，他能说什么？他没有信息来判断这个数字对不对

2. **Ship Package 是中间产物**
   - 它是 Solution Pro → Super Loop 的桥梁
   - 就像编译器内部的 AST——用户不需要审查 AST，只需要看编译结果

3. **强制审查会导致决策疲劳**
   - 8 个案例 × 每个 5-8 个 WP = 40-64 个 WP 需要审查
   - 这会彻底摧毁用户体验

4. **正确的做法：摘要式通知**
   ```
   ✅ Ship Pro 已完成规划
   - 8 个 Work Packages，分 3 个阶段
   - 预估总工时：320 小时
   - 关键依赖：WP-003 → WP-005（支付系统集成）
   - [查看详情]（可选展开）
   
   → 自动进入执行阶段
   ```
   
   忠礼可以展开看详情（Progressive Disclosure），但不需要主动确认才能继续。

**实施信心：9/10**

---

### Q3: 如果 Ship Pro 变成 LLM 引导，忠礼如何信任它的输出质量？

**建议：通过结构化验证 + 可追溯性 + 异常标记来建立信任，而不是通过人工审查。**

具体策略：

#### 策略 1：结构化输出 + 自动校验

```json
{
  "validation_summary": {
    "total_wps": 8,
    "all_have_ac": true,
    "all_have_constraints": true,
    "dependency_graph_valid": true,
    "total_estimated_hours": 320,
    "warnings": [
      "WP-005 没有前置依赖但引用了 WP-003 的输出"
    ]
  }
}
```

Ship Pro 的输出必须有 schema 校验——不合规的输出自动拒绝，不需要忠礼审查。

#### 策略 2：可追溯性（Traceability）

每个 WP 的每个 AC 都应该能追溯到 final_result 或 RTM 中的具体内容：

```json
{
  "ac_id": "AC-001",
  "criterion": "支持至少3家AI供应商",
  "source": "final_result.architecture.core_components[2]",
  "confidence": 0.92
}
```

这样如果忠礼对某个 AC 有疑问，他可以一键跳到源头。但这是**按需**的，不是默认展示的。

#### 策略 3：异常标记（而非全量审查）

```
⚠️ Ship Pro 发现 2 个需要注意的点：
1. final_result 中没有 implementation_plan，Ship Pro 自行拆分为 3 阶段
2. RTM 中有 3 个需求未被任何 WP 覆盖

[处理建议] [忽略] [查看详情]
```

只有异常才需要忠礼注意。正常情况自动通过。

#### 策略 4：置信度评分

Ship Pro 对每个 WP 给出置信度：
- **高置信度（>0.8）**：自动通过
- **中置信度（0.5-0.8）**：标记为"建议审查"
- **低置信度（<0.5）**：暂停，等待忠礼确认

这是 Selective HITL 的典型应用。

**实施信心：8/10**

> 理由：结构化验证 + 异常标记是成熟模式（Copilot 的 Code Scanning 就用类似策略）。但 LLM 输出的置信度评分本身可能不准确——需要校准。

### Q4: "Blueprint" 这个概念对忠礼有意义吗？

**建议：没有意义。忠礼只关心"方案"和"结果"。**

分析：

| 概念 | 忠礼的理解 | 实际对应 | 是否需要暴露给忠礼 |
|------|-----------|---------|:-:|
| Blueprint | ？？？ | frozen/living_blueprint | ❌ |
| 方案 | "AI 给我的解决方案" | final_result | ✅ |
| 任务拆解 | "AI 把方案分成了几步" | Ship Package / WPs | ⚠️ 摘要可见 |
| 执行计划 | "AI 开始写代码了" | Super Loop 执行 | ⚠️ 状态可见 |
| 结果 | "最终交付物" | 代码 + 文档 + RTM | ✅ |

**Blueprint 是内部技术概念**，对应的是 Solution Pro 内部对方案的结构化表示。忠礼不需要知道这个概念的存在——他只需要看"方案"（final_result 的人类可读版本）。

**砍掉 Blueprint 的用户可见性后**：
- 忠礼的界面简化为：方案 → 进度 → 结果
- 不再有"Blueprint 冻结"、"Blueprint 同步"等令人困惑的术语
- 技术复杂性被封装在 AI 层内部

**实施信心：10/10**

> 这个信心最高。Blueprint 从未对用户产生过价值——它是内部数据结构的泄露。

### Q5: 从用户视角，修正方案的整体评价

**总体评价：修正方向正确，但需要注意"LLM 引导"带来的信任挑战。**

#### 5.1 正确的部分

| 决策 | 评价 | 理由 |
|------|------|------|
| 砍掉 frozen_blueprint | ✅ 完全正确 | 32% 保真度的中间产物没有存在价值 |
| 砍掉 living_blueprint | ✅ 正确 | 结构不稳定，信息已在 final_result 中 |
| Ship Pro 升级为 LLM 引导 | ✅ 方向正确 | 能处理 final_result 的格式多样性 |
| 读 3 个文件（final_result + RTM + execution_plan） | ✅ 足够 | living_blueprint 的 design_decisions 价值有限 |
| `_ship_pro_hints` 约定 | ⚠️ 谨慎 | 增加了 Solution Pro 的耦合度 |

#### 5.2 需要注意的风险

**风险 1：LLM 引导的不可预测性**

确定性编译器的输出是可预测的——同样的输入永远产生同样的输出。LLM 引导编译器不是。

**缓解措施**：
- Ship Pro 的输出必须有严格的 JSON Schema 校验
- 校验失败的输出自动拒绝并重新生成（最多 3 次）
- 如果 3 次都失败，降级为确定性编译器（保留旧代码作为 fallback）

**风险 2：`_ship_pro_hints` 的耦合问题**

让 Solution Pro 输出一个"导航字段"指向关键数据位置，这意味着：
- 每次 Solution Pro 的 final_result 格式变化，都需要更新 `_ship_pro_hints` 的生成逻辑
- 这是一个维护负担

**替代方案**：
- 不让 Solution Pro 生成 hints
- 让 Ship Pro 的 LLM 自己探索 final_result 的结构（LLM 擅长这个）
- 只在 LLM 无法定位关键信息时，才使用 hints 作为 fallback

**风险 3：工时估算的准确性**

Ship Pro 新增了"工时估算"能力。但 LLM 的工时估算通常不准确（倾向于乐观）。

**缓解措施**：
- 工时估算标注为"AI 估算，仅供参考"
- 提供估算范围而非精确值（如 "30-50 小时" 而非 "40 小时"）
- 随着案例积累，建立历史数据校准模型

```
┌─────────────────────────────────────────────────────────────────┐
│ 忠礼的工作流（2 个决策点）                                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ① 忠礼提出想法                                                  │
│     "我要做一个跨境算力中转站"                                     │
│                                                                 │
│  ② Solution Pro 生成方案（~30分钟）                               │

│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 4.2 信息展示策略（Progressive Disclosure）

| 层级 | 展示内容 | 触发条件 |
|------|---------|---------|
| **L1: 摘要** | 方案一句话总结 + 3-5 个关键指标 | 默认展示 |
| **L2: 概览** | 核心架构 + 设计决策 + 需求覆盖 | 点击"查看详情" |
| **L3: 详情** | 完整 final_result + RTM + 执行计划 | 点击"展开全部" |
| **L4: 原始数据** | JSON 原始输出 | 仅开发者模式 |

### 4.3 通知策略（避免决策疲劳）

| 事件 | 通知方式 | 需要操作？ |
|------|---------|:-:|
| 方案生成完成 | 弹窗 + 摘要 | ✅ 需要确认 |
| Ship Pro 规划完成（无异常） | 静默通知 | ❌ 不需要 |
| Ship Pro 规划完成（有异常） | 通知 + 异常摘要 | ⚠️ 可能需要 |
| WP 执行进度（每 25%） | 静默进度条 | ❌ 不需要 |
| 全部 WP 完成 | 通知 + 结果摘要 | ✅ 需要验收 |
| 执行中遇到阻塞 | 即时通知 + 建议 | ⚠️ 可能需要 |

## 五、对 Q1-Q5（架构评审问题）的产品视角建议

### Q1: Ship Pro 用 LLM 还是确定性编译器？

**产品建议：LLM 引导 + 确定性 fallback。**

用户体验角度：
- LLM 能处理格式多样性 → 减少"因为格式问题导致流程中断"的糟糕体验
- 但 LLM 的不可预测性需要兜底 → 保留确定性编译器作为 fallback
- 用户不需要知道用的是哪种方式——他们只关心结果对不对

**实施信心：8/10**

### Q2: Ship Pro 应该读几个文件？

**产品建议：3 个文件足够（final_result + RTM + execution_plan）。**

- living_blueprint 的 design_decisions 价值有限（final_result 已包含设计理由）
- 读更多文件 = 更多 LLM token = 更慢 = 更贵 = 用户等待更久
- 用户体验优先级：速度 > 完整性

**实施信心：9/10**

### Q3: `_ship_pro_hints` 约定是否可行？

**产品建议：可行，但作为 optional fallback，不是 required。**

- 如果 Solution Pro 能生成 hints → 用 hints 精确定位
- 如果不能 → LLM 自己探索（LLM 完全有能力理解 JSON 结构）
- 不要让 hints 成为 Solution Pro 和 Ship Pro 之间的硬耦合

**实施信心：7/10**

### Q4: 砍掉 blueprint freezing 后，格式稳定性如何保证？

**产品建议：Ship Pro 的 JSON Schema 校验就是格式稳定性的保证。**

- 不管 Solution Pro 输出什么格式，Ship Pro 的输出必须符合固定 schema
- 下游（Super Loop）只和 Ship Pro 的 schema 打交道
- 格式多样性的问题在 Ship Pro 层被吸收，不向下游传播

**实施信心：9/10**

### Q5: 确定性 → LLM 引导的维护成本变化？

**产品建议：代码量减少，但测试成本增加。**

| 维度 | 确定性编译器 | LLM 引导编译器 |
|------|-------------|---------------|
| 代码量 | ~1048 行 Python | ~300 行 Python + prompts |
| 维护成本 | 中（格式变化需要改代码） | 低（LLM 自适应格式变化） |
| 测试成本 | 低（确定性，测一次就够） | 高（需要多次运行验证一致性） |
| 运行成本 | 几乎为 0 | 每次 ~$0.5-2（LLM API） |
| 调试难度 | 低（可复现） | 中（不可完全复现） |

**净效果**：总维护成本可能降低，但需要建立新的测试基础设施（LLM 输出的统计测试）。

**实施信心：7/10**

## 六、盲点与风险

### 6.1 修正方案的盲点

**盲点 1：没有考虑忠礼的"控制感"需求**

即使忠礼不需要逐步审查 Ship Package，他可能需要**感觉**自己在控制流程。

**建议**：
- 提供"执行仪表盘"——实时展示进度、已完成的 WP、正在进行的 WP
- 提供"随时暂停"能力——忠礼可以在任何时刻暂停执行
- 提供"回退"能力——如果对结果不满意，可以回退到方案阶段重新规划

**盲点 2：没有考虑"方案修改"的级联效应**

如果忠礼在 DP-1 修改了方案，Ship Pro 需要重新规划。但如果执行到一半忠礼要改方案呢？

**建议**：
- 明确"方案修改窗口"——只在 DP-1 确认时接受方案修改
- 执行阶段的修改走"变更请求"流程（而不是直接修改方案）
- 变更请求的影响评估由 Ship Pro 自动完成

**盲点 3：没有考虑多案例并行场景**

如果忠礼同时启动多个方案（不同 topic），他需要跨案例的视图。

**建议**：
- 提供"案例列表"视图——所有进行中/已完成案例的状态
- 但这不是 V1 优先级——先做好单案例体验

### 6.2 最大风险

**最大风险：Ship Pro 的 LLM 输出质量不稳定**

如果 Ship Pro 生成的 WP 质量差（AC 不可验证、工时估算离谱、依赖关系错误），下游 Super Loop 会产出低质量代码。而且这个问题可能在多个 WP 上级联。

**缓解措施**：
1. Ship Pro 输出必须有自动化质量检查（schema 校验 + 逻辑校验）
2. 低置信度的 WP 自动标记为"需要审查"
3. 建立"Ship Pro 质量评分"指标，持续监控
4. 保留确定性编译器作为 fallback

## 七、总结与建议

### 7.1 核心建议

| 编号 | 建议 | 信心 | 优先级 |
|------|------|:----:|:------:|
| 1 | 只设 2 个决策点（方案确认 + 结果验收） | 9/10 | P0 |
| 2 | Ship Package 不暴露为需确认的 artifact | 9/10 | P0 |
| 3 | 用异常标记代替全量审查 | 8/10 | P0 |
| 4 | 砍掉"Blueprint"概念的用户可见性 | 10/10 | P0 |
| 5 | Progressive Disclosure 分层展示 | 9/10 | P1 |
| 6 | LLM 引导 + 确定性 fallback | 8/10 | P1 |
| 7 | 提供控制感（仪表盘 + 暂停 + 回退） | 8/10 | P1 |
| 8 | 明确方案修改窗口，防止级联 | 7/10 | P2 |

### 7.2 一句话总结

> **忠礼需要的是"方案→确认→结果"的简洁流程，中间的 Ship Package 是 AI 的内部工件，不应该成为用户的决策负担。用异常标记代替全量审查，用 Progressive Disclosure 代替信息倾倒，用控制感（仪表盘+暂停+回退）代替逐步确认。**
