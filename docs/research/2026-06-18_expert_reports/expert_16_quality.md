# 专家 16：AI 质量工程师 — Agent 审核 Agent 模式设计

> **日期**: 2026-06-18
> **角色**: AI 质量工程师，专注"用 AI 审核 AI"的模式设计
> **评审对象**: Ship Pro 输出质量保障方案

---

## 一、核心立场

**质量保障本身也应该是 AI Native 的——但 AI 审核不是银弹，需要和确定性校验互补。**

经过对 LLM-as-judge、对抗性 Agent、多 Agent 共识、Constitutional AI 等领域的系统研究，我的结论是：

- ✅ AI 审核 Agent 是**必要的**，因为 ship_package.json 的质量维度超出了 JSON Schema 能覆盖的范围
- ⚠️ AI 审核 Agent **不能替代**确定性校验，而是**补充**它
- 🔑 关键设计挑战不是"能不能审核"，而是"如何避免审核者和生产者共谋"

---

## 二、推荐的审核 Agent 设计

### 2.1 架构：分层审核（不是单一审核者）

```
Ship Pro（生产 Agent）
  输出：ship_package.json
      │
      ▼
┌─────────────────────────────────────┐
│  Layer 1: 确定性校验（JSON Schema）   │  ← 必须通过，否则不进入 Layer 2
│  - 结构完整性                         │
│  - 字段类型正确                       │
│  - 引用完整性（WP 引用的需求 ID 存在）  │
└─────────────────────────────────────┘
      │ 通过
      ▼
┌─────────────────────────────────────┐
│  Layer 2: AI 审核 Agent              │  ← 本报告核心
│  - 语义质量审核                       │
│  - 可执行性评估                       │
│  - 需求覆盖深度分析                   │
│  - 工时合理性判断                     │
└─────────────────────────────────────┘
      │ 通过/不通过
      ▼
  输出到 Super Loop
```

**为什么分层？**
- Layer 1 是 100% 确定性的，零误判率。如果结构都不对，没必要浪费 LLM token 做语义审核
- Layer 2 处理的是"灰色地带"——结构正确但质量不够。这正是 LLM 擅长的领域

### 2.2 审核 Agent 的角色定义

审核 Agent 不是"通用评审员"，而是**三个专业审核角色的集合**：

| 审核角色 | 关注点 | 类比 |
|---------|--------|------|
| **需求审计师** | 需求覆盖是否完整？验收标准是否可验证？ | QA Lead |
| **架构评审员** | 工作包拆分是否合理？依赖关系是否正确？ | Tech Lead |
| **项目经理** | 工时估算是否合理？阶段划分是否可执行？ | PM |

**实现方式**：不是 spawn 3 个 Agent，而是在一个 prompt 中定义 3 个审核视角，要求 Agent 逐维度输出审核意见。这比多 Agent 共识更简单且足够有效。

### 2.3 审核 Prompt 设计原则

基于 Constitutional AI 的"reason-based alignment"理念：

```
你不是在检查格式。你是在判断：
"如果 Super Loop 拿到这个 ship_package，能不能直接开始编码？"

对每个维度，给出：
1. 判断（通过/不通过/需修改）
2. 理由（为什么这样判断）
3. 具体修改建议（如果不通过）

不要为了"通过"而降低标准。宁可误判不通过，也不要放过有问题的输出。
```

**关键设计**：
- 不用 1-10 分（研究表明 LLM 评分在数字尺度上不稳定）
- 使用**离散命名类别**：`通过` / `需修改` / `不通过`（对应 LLM-as-judge 最佳实践）
- 要求**理由先行**（Chain-of-thought），再给判断

## 三、审核维度和评分标准

### 3.1 六维审核模型

| 维度 | 权重 | 审核内容 | 判断标准 |
|------|------|---------|---------|
| **D1: 需求覆盖完整性** | 25% | 每个 RTM 中的需求是否被至少一个 WP 覆盖 | 覆盖率 < 100% → 不通过 |
| **D2: 验收标准可验证性** | 20% | AC 是否具体到可以写测试用例 | 有模糊 AC（如"系统应高效"）→ 需修改 |
| **D3: 工作包拆分合理性** | 20% | WP 粒度是否适中（20-80h），无过大/过小 | WP < 8h 或 > 120h → 需修改 |
| **D4: 依赖关系正确性** | 15% | 依赖链是否无环，是否反映真实技术依赖 | 有循环依赖 → 不通过 |
| **D5: 工时估算合理性** | 10% | 总工时是否在合理范围（±30% 基准） | 偏差 > 50% → 需修改 |
| **D6: 技术约束一致性** | 10% | 技术约束是否与 final_result 一致 | 有矛盾 → 需修改 |

### 3.2 各维度详细审核标准

#### D1: 需求覆盖完整性（25%）

```
审核方法：
1. 从 RTM 提取所有 requirement_id
2. 从 ship_package 提取所有 WP 的 covered_requirements
3. 计算覆盖率 = covered / total
4. 检查每个被覆盖的需求是否有对应的 AC

判断：
- 覆盖率 = 100% 且每个需求有 AC → 通过
- 覆盖率 ≥ 90% 且缺失的是低优先级需求 → 需修改
- 覆盖率 < 90% → 不通过
```

**这个维度其实可以确定性实现**——见第五节对比分析。

#### D2: 验收标准可验证性（20%）

```
审核方法：
对每个 AC，判断是否满足 SMART 原则：
- Specific（具体）：不是"系统应高效"，而是"P99 延迟 < 200ms"
- Measurable（可测量）：可以写自动化测试验证
- Achievable（可实现）：技术上可行
- Relevant（相关）：与 WP 目标直接相关
- Time-bound（有时限）：在 WP 范围内可完成

典型不通过案例：
- "用户体验良好" → 不具体
- "支持高并发" → 无量化指标
- "代码质量高" → 不可测量
```

**这是 AI 审核的核心价值所在**——JSON Schema 无法判断 AC 的语义质量。

#### D3: 工作包拆分合理性（20%）

```
审核方法：
1. 检查 WP 粒度：
   - estimated_hours < 8h → 过细（可能是任务不是 WP）
   - estimated_hours > 120h → 过粗（应该拆分）
2. 检查 WP 内聚性：
   - 一个 WP 是否只关注一个技术模块？
   - 还是把不相关的东西混在一起？
3. 检查 WP 间耦合度：
   - 依赖关系是否清晰？
   - 是否存在隐式依赖未声明？

判断：
- 所有 WP 在 8-120h 范围且内聚 → 通过
- 有 1-2 个 WP 超出范围但可接受 → 需修改
- 有 WP > 200h 或多个 WP 内聚性差 → 不通过
```

#### D4: 依赖关系正确性（15%）

```
审核方法：
1. 构建依赖图（WP 为节点，dependencies 为边）
2. 检查是否有环（拓扑排序）
3. 检查依赖方向是否合理（基础设施 → 业务逻辑 → 集成）
4. 检查是否有"孤立 WP"（无依赖且不被依赖的独立 WP 是否合理）

判断：
- 无环 + 依赖方向合理 → 通过
- 无环但有方向问题（如业务逻辑依赖 UI）→ 需修改
- 有环 → 不通过
```

**注意**：环检测可以确定性实现，但"依赖方向是否合理"需要 AI 判断。

#### D5: 工时估算合理性（10%）

```
审核方法：
1. 计算总工时 = sum(estimated_hours)
2. 与基准对比（基于项目复杂度和团队规模）
3. 检查各 WP 工时分配比例是否合理

基准参考（来自 8 个案例分析）：
- 小型项目（3-5 WP）：200-500h
- 中型项目（6-10 WP）：500-1500h
- 大型项目（10+ WP）：1500-4000h

判断：
- 偏差在 ±30% 内 → 通过
- 偏差 30-50% → 需修改
- 偏差 > 50% → 不通过
```

**注意**：工时估算本质上是"有根据的猜测"，AI 审核的价值在于发现明显不合理的估算（如一个完整微服务估 16h）。

#### D6: 技术约束一致性（10%）

```
审核方法：
1. 从 final_result 提取技术栈和约束
2. 从 ship_package 提取 technical_constraints
3. 检查是否一致（不是要求完全相同，而是不矛盾）

典型不通过案例：
- final_result 说"使用 PostgreSQL"，ship_package 说"MongoDB"
- final_result 说"部署在 AWS"，ship_package 说"部署在 Railway"
- final_result 说"必须支持离线"，ship_package 无离线相关约束
```

### 3.3 综合判断逻辑

```
不通过条件（任一触发）：
- D1 覆盖率 < 90%
- D4 有循环依赖
- 3 个以上维度为"不通过"

需修改条件：
- D1 覆盖率 90-99%
- D2 有模糊 AC（但大部分可验证）
- D3 有 1-2 个 WP 粒度不当
- D5 工时偏差 30-50%

通过条件：
- 所有维度为"通过"或"需修改"
- "需修改"维度不超过 2 个
- 无"不通过"维度
```

## 四、如何避免审核者和生产者"共谋"

这是最核心的设计挑战。两个 Agent 用同一个 LLM，可能有同样的盲区。

### 4.1 共谋风险分析

| 共谋类型 | 表现 | 风险等级 |
|---------|------|---------|
| **盲区共谋** | 两者都忽略同一类问题（如都低估测试工时） | 🔴 高 |
| **风格偏好** | 审核者偏好生产者的写作风格，给高分 | 🟡 中 |
| **信息不对称** | 审核者无法访问生产者的推理过程 | 🟡 中 |
| **模型局限** | 同一模型的能力上限 = 审核的能力上限 | 🔴 高 |

### 4.2 反共谋设计

#### 策略 1：异构模型（最有效但成本高）

```
生产 Agent：Claude 3.5 Sonnet（或当前模型）
审核 Agent：GPT-4o / Gemini 2.5 Pro（不同模型家族）

原理：不同模型有不同的训练数据和对齐策略，盲区不完全重叠
效果：可以捕获"模型特定盲区"
成本：需要额外 API 调用，延迟增加
```

**推荐**：如果预算允许，审核 Agent 用不同模型家族。这是最可靠的反共谋策略。

#### 策略 2：对抗性 Prompt（低成本）

```
审核 Agent 的 prompt 中显式包含：

"你的角色是'挑刺者'，不是'确认者'。
你的任务不是确认 ship_package 有多好，而是找出它的问题。
假设 ship_package 有至少 3 个问题，找到它们。

常见盲区（你必须检查）：
- 工时估算是否过于乐观？（LLM 普遍低估实现复杂度）
- 验收标准是否真的可测试？（LLM 倾向于写模糊的 AC）
- 是否遗漏了非功能性需求？（性能、安全、可观测性）
- 依赖关系是否过于简化？（真实项目有更多隐式依赖）"
```

**原理**：通过 prompt 注入"对抗性心态"，打破 LLM 的"讨好倾向"（sycophancy）

#### 策略 3：交叉验证（中等成本）

```
不只有一个审核 Agent，而是：
- 审核 Agent A：关注需求覆盖 + AC 质量
- 审核 Agent B：关注技术架构 + 工时估算
- 如果 A 和 B 的判断冲突 → 触发人工审核

原理： specialization reduces sycophancy（专门化减少讨好）
效果：比单一审核者更可靠，但增加 2x 审核成本
```

#### 策略 4：Golden Dataset 校准（持续运营）

```
维护一组"已知答案"的 ship_package：
- 3 个"应该通过"的高质量样本
- 3 个"应该不通过"的低质量样本（含已知问题）

每次审核 Agent 运行后，用 golden dataset 校准：
- 如果审核者放过了一个已知低质量样本 → 审核标准需要调严
- 如果审核者误判了一个已知高质量样本 → 审核标准需要调松
```

**原理**：来自 Constitutional AI 的"multi-method audit pipeline"——用 205 个可测试原则分解 constitution，持续校准模型行为。

### 4.3 推荐方案

**短期（MVP）**：策略 2（对抗性 Prompt）+ 策略 4（Golden Dataset 校准）
**中期（稳定后）**：+ 策略 1（异构模型）
**长期（规模化）**：+ 策略 3（交叉验证）

## 五、审核不通过的处理流程

### 5.1 修复流程设计

```
审核不通过
    │
    ▼
┌─────────────────────────────────────┐
│  Step 1: 分类不通过原因              │
│  - 结构性问题（D1/D4）→ 确定性修复   │
│  - 语义性问题（D2/D3/D5/D6）→ AI 修复│
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│  Step 2: 修复策略                    │
│                                      │
│  情况 A：单个维度"需修改"            │
│  → 让 Ship Pro 根据审核意见修改      │
│  → 修改后重新审核（最多 2 轮）       │
│                                      │
│  情况 B：多个维度"不通过"            │
│  → 分析根因：是输入质量问题？         │
│    → 是：标记 Solution Pro 输出问题   │
│    → 否：Ship Pro 重新生成           │
│                                      │
│  情况 C：2 轮修改后仍不通过           │
│  → 升级到人工审核                    │
│  → 同时记录 case 用于改进            │
└─────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────┐
│  Step 3: 学习闭环                    │
│  - 记录：什么问题 → 怎么修的         │
│  - 更新：审核 prompt 或 golden dataset│
│  - 反馈：给 Ship Pro 的 prompt 改进  │
└─────────────────────────────────────┘
```

### 5.2 修复轮次控制

```
最大修复轮次：2 轮

轮次 1：Ship Pro 收到审核意见，修改 ship_package
轮次 2：审核 Agent 再次审核
  - 通过 → 输出
  - 仍不通过 → 进入轮次 3

轮次 3（最终）：
  - 如果问题集中在 1 个维度 → 人工修改该维度
  - 如果问题分散 → 人工全面审核

为什么限制 2 轮？
- 研究表明 LLM-LMM 修复循环在 2 轮后收益递减
- 超过 2 轮通常意味着输入质量问题，不是 Ship Pro 的问题
- 避免无限循环消耗 token
```

### 5.3 不通过的降级策略

```
如果最终无法通过审核：

降级方案 1：人工编辑模式
- 输出当前 ship_package + 审核意见
- 人工在编辑器中修改
- 修改后跳过审核直接输出（信任人工判断）

降级方案 2：部分输出模式
- 输出"已通过的 WP"（审核通过的 WP 直接进入 Super Loop）
- "未通过的 WP"标记为"需人工确认"
- 人工只处理有问题的部分

降级方案 3：参考输出模式
- 输出 ship_package 作为"参考草案"
- 不直接进入 Super Loop
- 人工基于草案创建最终版本
```

## 六、同步 vs 异步审核

### 6.1 方案对比

| 模式 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **全量同步** | 每次生成都审核 | 质量最高 | 延迟 2x，成本 2x |
| **全量异步** | 生成后异步审核，不阻塞 | 不增加延迟 | 发现问题时已经太晚 |
| **抽检** | 随机抽取 30% 审核 | 成本可控 | 60% 的输出未经审核 |
| **风险分级** | 高风险全审，低风险抽检 | 平衡质量和成本 | 需要定义"高风险" |

### 6.2 推荐：风险分级审核

```
高风险（必须审核）：
- 项目总工时 > 1000h
- WP 数量 > 10
- 首次使用 Ship Pro 的用户
- 上次审核有"不通过"记录

中风险（50% 抽检）：
- 项目总工时 300-1000h
- WP 数量 5-10
- 有使用历史且上次通过

低风险（10% 抽检）：
- 项目总工时 < 300h
- WP 数量 < 5
- 连续 3 次审核通过的用户
```

**原理**：来自 AI QA 领域的"risk-based quality"——不追求 100% 覆盖，而是最大化风险覆盖。

### 6.3 实现方式

```python
# 伪代码
def should_review(ship_package, user_history):
    risk_score = calculate_risk(ship_package, user_history)
    
    if risk_score >= HIGH_THRESHOLD:
        return True  # 必须审核
    elif risk_score >= MEDIUM_THRESHOLD:
        return random() < 0.5  # 50% 抽检
    else:
        return random() < 0.1  # 10% 抽检

def calculate_risk(ship_package, user_history):
    score = 0
    total_hours = sum(wp.estimated_hours for wp in ship_package.work_packages)
    
    if total_hours > 1000: score += 3
    elif total_hours > 300: score += 2
    else: score += 1
    
    if len(ship_package.work_packages) > 10: score += 2
    elif len(ship_package.work_packages) > 5: score += 1
    
    if user_history.last_review_status == "failed": score += 3
    if user_history.consecutive_passes >= 3: score -= 2
    
    return score
```

## 七、AI 审核 vs 确定性校验：对比分析

### 7.1 各维度最佳方案

| 审核维度 | 确定性方案 | AI 方案 | 推荐 | 理由 |
|---------|-----------|---------|------|------|
| **D1: 需求覆盖完整性** | ✅ 集合运算 | 也可以 | **确定性** | 100% 准确，零成本 |
| **D2: AC 可验证性** | ❌ 无法实现 | ✅ 语义理解 | **AI** | 需要理解自然语言 |
| **D3: WP 拆分合理性** | ⚠️ 只能检查范围 | ✅ 综合判断 | **混合** | 范围检查用确定性，内聚性用 AI |
| **D4: 依赖正确性** | ✅ 图算法 | 也可以 | **混合** | 环检测用确定性，方向合理性用 AI |
| **D5: 工时合理性** | ⚠️ 只能检查范围 | ✅ 经验判断 | **AI** | "合理性"本质是模糊判断 |
| **D6: 约束一致性** | ⚠️ 关键词匹配 | ✅ 语义对比 | **AI** | 需要理解技术语义 |

### 7.2 混合方案（推荐）

```
Layer 1（确定性，必须通过）：
├── JSON Schema 校验（结构完整性）
├── D1: 需求覆盖率计算（集合运算）
├── D4-部分: 循环依赖检测（拓扑排序）
└── D3-部分: WP 工时范围检查（数值比较）

Layer 2（AI 审核，处理灰色地带）：
├── D2: AC 可验证性评估
├── D3-部分: WP 内聚性判断
├── D4-部分: 依赖方向合理性
├── D5: 工时估算合理性
└── D6: 技术约束一致性
```

**为什么不全用 AI？**
- 确定性校验成本 ≈ 0，AI 审核成本 > 0
- 确定性校验 100% 可重复，AI 审核有随机性
- 确定性校验速度快（ms 级），AI 审核慢（秒级）

**为什么不全用确定性？**
- AC 质量、工时合理性、依赖方向合理性——这些需要"理解"，不是规则能覆盖的
- 这正是 AI Native 的价值：用理解力处理模糊问题

### 7.3 成本估算

```
确定性 Layer 1：
- 成本：≈ 0（纯计算）
- 延迟：< 100ms
- 准确率：100%（对它能检查的维度）

AI Layer 2：
- 成本：~2000-4000 tokens/次（输入 ship_package + 审核 prompt + 输出审核意见）
- 延迟：3-8 秒
- 准确率：~85-90%（基于 LLM-as-judge 研究）

风险分级后：
- 高风险 100% 审核
- 中风险 50% 审核
- 低风险 10% 审核
- 平均审核率：~40%（假设项目风险分布均匀）

每次审核成本：~$0.01-0.03（取决于模型）
每个项目平均增加成本：~$0.004-0.012
```

## 十一、对 Q1-Q5 的回答

### Q1: Ship Pro 用 LLM 还是确定性编译器？

**混合方案**：LLM 做"理解"（解析不统一的 final_result），确定性代码做"组装"（生成 ship_package.json）。质量保障也用混合：确定性校验结构 + AI 审核语义。

### Q2: 是否需要额外的校验层？

**需要，但不是纯 AI 校验层**。是"确定性校验 + AI 审核"的分层方案。确定性层处理可计算的质量维度，AI 层处理需要理解的质量维度。

### Q3: 审核 Agent 应该审核什么？

**6 个维度**：需求覆盖完整性、AC 可验证性、WP 拆分合理性、依赖正确性、工时合理性、约束一致性。其中 D1 和 D4-部分可以用确定性实现，其余用 AI。

### Q4: 每次都要审核吗？

**不推荐每次**。用风险分级：高风险项目全审，中风险 50% 抽检，低风险 10% 抽检。平均审核率约 40%，在保证质量的同时控制成本。

### Q5: 与"纯 JSON Schema"方案的对比？

| | 纯 JSON Schema | 纯 AI 审核 | 混合方案（推荐） |
|---|---|---|---|
| 结构完整性 | ✅ 100% | ⚠️ ~90% | ✅ 100% |
| 语义质量 | ❌ 0% | ✅ ~85% | ✅ ~85% |
| 成本 | ≈ 0 | 中 | 低-中 |
| 延迟 | < 100ms | 3-8s | < 100ms + 条件性 3-8s |
| 可重复性 | ✅ 100% | ⚠️ ~85% | ✅ 确定性部分 100% |
| 覆盖面 | 窄（只能检查结构） | 广（可检查语义） | 广 |

## 十二、AI Native 反思

> 这次设计是否 AI Native？
>
> **用对了**：
> - 没有试图用 regex/if-else 覆盖所有质量维度
> - 承认"AC 可验证性"和"工时合理性"需要理解力，不是规则能处理的
> - 借鉴了 Constitutional AI 的"reason-based"理念，而不是写一堆检查规则
>
> **退化的地方**：
> - 风险分级的阈值设计还是偏向"定义规则"（如果 > 1000h → 高风险）
> - 更 AI Native 的做法是：让 AI 自己判断风险等级，而不是我定义阈值
>
> **下次改进**：
> - 风险分级本身也可以用 AI 判断——给审核 Agent 一组历史案例，让它判断新项目是否需要审核
> - 这才是真正的"用 AI 审核 AI"——不只是审核输出，还审核"是否需要审核"
