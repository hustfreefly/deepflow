# Phase 0 评审：测试覆盖度

> **评审日期**: 2026-06-18
> **评审视角**: 测试策略审计
> **评审范围**: Phase 0 测试案例目录 + 输入格式分析 + Eval 测试代码 + Phase 1-2 测试计划

---

## 评审结论：PASS_WITH_CONCERNS

Phase 0 的测试体系有合理骨架：8 个案例覆盖了 3 种主要输入格式 + 2 个边界极端，Eval 测试（test_eval_checks.py）对 ship_package 输出质量做了 5 维检查。但存在 **6 个明确盲区** 和 **3 个计划可行性风险**，需要在 Phase 1 启动前补齐。

### 3.2 Eval 测试盲区

| 盲区 | 严重度 | 说明 |
|------|:------:|------|
| **budget 边界值** | 高 | 未测试 tokens=0、time_minutes=0、负数、超大值（如 999999） |
| **WP ID 重复** | 高 | 两个 WP 使用相同 ID 的场景未覆盖 |
| **依赖引用不存在的 WP（非 WP-999）** | 中 | 仅测试了 WP-999，未测试其他格式的无效引用 |
| **AC 全为 L1 的极端包** | 中 | bad_package 混合了 L1-L4，未测试"全部不可验证"场景 |
| **model_tier 枚举校验** | 中 | Schema 测试未覆盖 model_tier 的合法值（fast/standard/slow） |
| **acceptance_tests 字段** | 低 | 有该字段的 WP 和没有的 WP 混合场景未测试 |
| **并发/幂等性** | 中 | 同一包连续跑两次 check，结果是否一致 |
| **NaN/Infinity 数值** | 低 | budget.tokens 为浮点数或 NaN 时的行为 |
| **深度嵌套 JSON** | 低 | 超深嵌套（>10 层）是否导致栈溢出 |

## 4. 集成测试计划评审

### 4.1 开发计划中的 Phase 2 测试

开发计划定义了以下 Phase 2 测试活动：

| 计划项 | 评价 | 风险 |
|--------|:----:|------|
| 端到端测试 5-8 个案例 | 🟢 合理 | 案例数足够 |
| 评估三层质量评估效果 | 🟡 模糊 | "L1 自检命中率"如何量化？无明确指标 |
| 评估反馈闭环效果 | 🟢 合理 | 收敛轮数、修改质量可量化 |
| 评估 Token 消耗 | 🟢 合理 | 有明确预算（<100K） |
| 同一案例跑 3 次，波动 < 10% | 🟠 有缺陷 | 见下方分析 |

### 4.2 "跑 3 次" 稳定性验证的问题

**当前计划**：同一案例跑 3 次，检查关键指标波动 < 10%。

**问题 1：样本量不足**
- 3 次运行只能看极差（max-min），无法计算标准差或置信区间
- 如果 3 次中有 1 次异常（LLM 常见的"坏轮次"），无法判断是偶发还是系统性

**建议**：
- 至少 5 次运行（推荐 7 次）
- 报告 mean ± stddev，而非仅看极差
- 定义"关键指标"的明确列表：WP 数量、AC 平均分、依赖边数、Token 消耗

**问题 2：缺少"通过/失败"判定标准**
- "波动 < 10%" 是对什么指标？WP 数量波动 10% 意味着什么？
- 如果 TC-01 第一次产出 8 个 WP，第二次产出 9 个（波动 12.5%），算失败吗？

**建议**：
- 按指标类型分别定义稳定性标准：
  - 离散指标（WP 数量）：允许 ±1
  - 连续指标（AC 平均分）：CV（变异系数）< 15%
  - 资源指标（Token 消耗）：允许 ±30%（LLM token 天然波动大）

**问题 3：未考虑 prompt 版本变化**
- 如果 Phase 1 迭代中修改了 prompt，3 次运行跨版本，结果不可比

**建议**：
- 稳定性测试必须在固定 prompt 版本下执行
- 记录 `_meta.prompt_sha` 确保可追溯

## 5. 缺失测试场景

### 5.1 完全未覆盖的场景（按优先级排序）

| # | 场景 | 优先级 | 理由 |
|---|------|:------:|------|
| 1 | **截断/损坏 JSON 输入** | 🔴 P0 | 真实场景中文件写入中断、网络超时都可能导致 JSON 不完整。系统必须优雅处理。 |
| 2 | **字段类型错误**（如 components 是字符串而非数组） | 🔴 P0 | 上游 Solution Pro 可能输出非预期类型。当前 Eval 仅测试了 budget 类型错误。 |
| 3 | **超大输入（>50KB final_result）** | 🟠 P1 | 企业级方案可能非常大。需确认 LLM context window 是否够用，是否需要截断策略。 |
| 4 | **组件字段归一化** | 🟠 P1 | 输入分析识别了 5 种组件字段命名变体，但无测试验证 Architect 能否正确归一化。 |
| 5 | **多语言混合输入**（中/英/日混用） | 🟡 P2 | 部分 Solution Pro 输出可能包含多语言内容。 |
| 6 | **空 architecture 字段**（`"architecture": {}`） | 🟡 P2 | 有 architecture 字段但内容为空，不同于完全没有该字段。 |
| 7 | **重复组件名**（两个组件同名） | 🟡 P2 | 上游可能输出重复命名的组件，Architect 需要处理。 |
| 8 | **端到端幂等性**（同一输入两次完整运行，比较 ship_package） | 🟠 P1 | 不同于稳定性（看波动），幂等性关注"是否产出相同结构"。 |
| 9 | **反馈闭环压力测试**（Reviewer 连续 5 轮 FAIL） | 🟡 P2 | 验证 token 预算耗尽时的降级行为。 |
| 10 | **跨 Agent 数据一致性**（blueprint 中的组件数 vs wp_structure 中的 WP 数 vs ship_package 中的 WP 数） | 🟠 P1 | 确保数据在 Agent 间传递时不丢失。 |

### 5.2 Architect Agent 特有的测试缺口

输入格式分析定义了 5 项"必须提取"信息，但无测试验证提取质量：

| 必须提取信息 | 有测试案例？ | 有验证标准？ |
|------------|:----------:|:----------:|
| 模块/组件列表 | ✅ 有案例 | ❌ 无验证标准（提取多少算对？） |
| 组件职责描述 | ❌ 无案例 | ❌ 无验证标准 |
| 数据流/请求流 | ❌ 无案例 | ❌ 无验证标准 |
| 技术选型 | ✅ 有案例（TC-06） | ❌ 无验证标准 |
| 实施阶段 | ❌ 无案例 | ❌ 无验证标准 |

**核心问题**：我们有输入案例，但没有"期望输出"。没有 blueprint.json 的 ground truth，就无法衡量 Architect 的提取质量。

## 6. 具体建议

### 6.1 Phase 1 启动前必须完成（P0）

1. **构造 TC-09 和 TC-10**
   - 这两个案例已规划但未落地，是 Phase 1 边界测试的前置依赖
   - TC-09（单 WP）：可用最简单的项目（如"实现一个 TODO 应用"）
   - TC-10（10+ WP）：建议从 TC-01（12 组件）衍生，确保有足够的拆分空间

2. **准备 2 个异常输入案例**
   - TC-11：截断 JSON（在 TC-01 的中间位置截断）
   - TC-12：字段类型错误（components 为字符串而非数组）

3. **为 TC-01 编写 blueprint.json 期望输出（ground truth）**
   - 至少覆盖：组件列表（12 个）、数据流、技术选型
   - 用于验证 Architect Agent 的提取召回率和准确率

### 6.2 Phase 1 期间补充（P1）

4. **补充 Eval 测试盲区**
   - budget 边界值测试（tokens=0, 负数, 超大值）
   - WP ID 重复测试
   - 全 L1 AC 的极端包测试

5. **定义 Architect 输出验证标准**
   - 组件提取召回率：提取出的组件数 / 实际组件数
   - 组件提取准确率：正确提取的组件数 / 提取出的组件数
   - 信息保留率：提取出的字段数 / 应提取的字段数

6. **稳定性测试升级**
   - 从 3 次提升到 5-7 次
   - 报告 mean ± stddev
   - 按指标类型分别定义通过标准

### 6.3 Phase 2 期间补充（P2）

7. **端到端数据一致性检查**
   - 验证 blueprint 组件数 → wp_structure WP 数 → ship_package WP 数 的传递链
   - 允许合并（1 个组件 → 1 个 WP），但不允许无故丢失

8. **反馈闭环压力测试**
   - 故意构造一个"Reviewer 必定 FAIL"的场景（如 AC 全为 L1）
   - 验证 5 轮后的降级行为

9. **Token 消耗基线**
   - 记录每个案例的 Token 消耗
   - 建立"Token/组件数"的基线比率
   - 异常偏离时告警

## 7. 总结

| 维度 | 评分 | 说明 |
|------|:----:|------|
| 格式覆盖 | 🟡 70% | 3 种主格式 + 1 个变体覆盖，但 Format B-tech 仅 1 个案例，异常格式完全缺失 |
| 边界覆盖 | 🟡 60% | 空输入/极端小有覆盖，但 TC-09/TC-10 未落地，截断/损坏缺失 |
| Eval 测试 | 🟢 80% | 75 个测试覆盖 5 个维度，有少量盲区（budget 边界、ID 重复） |
| 集成测试计划 | 🟡 65% | 框架合理，但稳定性验证样本量不足、指标定义模糊 |
| 输出验证标准 | 🔴 30% | 最大缺口：有输入案例但无期望输出（ground truth），无法量化 Architect 质量 |

**总体评价**：测试体系的"骨架"是对的——知道要测什么维度、知道要覆盖什么格式。但"肌肉"不够——关键案例未构造（TC-09/10）、异常场景缺失、输出验证标准空白。建议在 Phase 1 启动前优先补齐 P0 项（约 0.5 天工作量），P1 项可在 Phase 1 期间并行完成。
