# 专家 #1 评审 — 信息架构师

## 评分（1-10）

| 维度 | 评分 | 简评 |
|------|------|------|
| 信息层次 | **7/10** | L0-L4 分层方向正确，但 L3/L4 语义边界模糊 |
| 信息密度 | **4/10** | 文件清单过多，架构图退化为目录树 |
| 可读性 | **5/10** | 新手 30 秒内无法建立心智模型，噪音淹没信号 |
| 数据流表达 | **3/10** | connector 只有一行文字，无方向性、无类型标注 |
| 视觉层级 | **5/10** | 四个 Domain 等权重平铺，无主次区分 |
| **总评** | **4.8/10** | 有骨架但缺灵魂，当前是"文件清单"而非"架构图" |

---

## 关键发现

### 1. L3 语义不纯：运行时数据与静态文档混层

L3 标注为"数据层"，但内部并列了 `Blackboard 运行时数据` 和 `文档 & 归档`。前者是**运行时状态**（JSON 文件协议），后者是**静态文档资产**。两者性质完全不同：
- Blackboard 是 L1 ↔ L2 之间的**通信协议**，应该作为 L1-L2 之间的"数据流层"出现
- docs/ 目录是项目文档，不应该出现在**系统架构图**中

一个不熟悉 DeepFlow 的人看到这里会困惑：文档目录为什么是架构的一层？

### 2. 文件清单密度远超架构图所需的信息密度

以 Solution Pro 为例，Domain 卡片内列出了：
- 核心逻辑 7 个文件
- 质量门禁 7 个文件
- Prompts & 配置 4 个条目
- 契约 1 个文件
- 管线步骤 6 个

**总计 25 个可视化元素塞进一张卡片**。架构图的目的是回答"这个模块负责什么、和其他模块怎么交互"，不是"这个模块有多少个文件"。`harness_scorer.py`、`harness_validator.py`、`harness_check_expert.py` 这三个文件名对理解架构的贡献极低——它们可以归结为一个概念："Quality Harness 子系统"。

### 3. Connector 箭头几乎没有信息量

三层之间的 connector 各只有一行文字：
- `sessions_spawn + exec`
- `domain dispatch + spawn Workers`
- `Blackboard 文件读写 + JSON 状态传递`

问题：
- 没有方向性标注（谁 → 谁？）
- 没有数据内容说明（传递的是什么？）
- 没有控制流与数据流的区分（Blackboard 是双向读写，但箭头是单向的 ▼）
- 三个 connector 视觉样式完全一致，无法区分"控制流"和"数据流"

### 4. 顶部统计数字是"虚荣指标"而非架构信息

Header 区域的 5 个 stat 数字（188K 行、1,481 文件、4 Domain、6 Contract、85.5% 有效代码）对项目汇报有意义，对理解架构无帮助。它们占据视觉焦点位置，但不帮助回答"系统如何工作"。

### 5. 四个 Domain 模块等权重平铺，缺乏主次

Spec Pro（9.5K 行）和 Solution Pro（15.3K 行）是核心，Investment（5.6K 行）和 Research Pro（2.7K 行）是附加模块。但四张卡片大小相同、样式相似、位置并列，没有任何视觉暗示告诉读者"先看哪两个"。

## 具体改进建议（按优先级排序）

### 🔴 必须改

1. **删除 L2 Domain 卡片中的文件清单，替换为"子系统"级别的抽象**
   - 当前：列出 `harness_scorer.py`、`harness_validator.py`、`harness_scoring.py`……
   - 应改为：`Quality Harness（评分/验证/契约检查）`
   - 原则：一个 Domain 卡片最多 5-7 个概念块，每个块是**角色**而非文件名

2. **重写 Connector：区分控制流与数据流，标注方向与内容**
   - 控制流（实线箭头）：谁 spawn 谁、谁调度谁
   - 数据流（虚线箭头）：Blackboard 读写路径、输入输出
   - 标注传递的内容：如 `spawn → LivingSpec 上下文`、`↔ Blackboard JSON`

3. **从 L3 移除文档归档，将 Blackboard 提升为独立的"通信层"**
   - Blackboard 不是"数据层"，它是 L1-L2 之间的**通信协议层**
   - 放在 L1 和 L2 之间（横向条），而非 L3（纵向层）
   - 文档归档完全移除架构图

4. **Header 统计数字缩减为 1-2 个核心指标**
   - 保留：Domain 数量（说明扩展性）
   - 移除：总行数、文件数、有效代码百分比（这些是 README 内容，不是架构信息）

### 🟡 建议改

5. **Domain 模块按主次分层排列**
   - 上层：Spec Pro + Solution Pro（左右并列，大卡片）
   - 下层：Investment + Research Pro（左右并列，小卡片，灰度降级）
   - 或用网格 + 视觉权重（大小、边框粗细、饱和度）区分

6. **L2 的 pipeline 步骤增加"并行/串行"标注**
   - Solution Pro 的 10 阶段管线中，`Workers 并行` 应明确标注 `||` 符号或并排布局
   - Spec Pro 的 `循环收集` 应画成循环箭头而非线性箭头

7. **每个 Domain 卡片增加一句话"架构职责"**
   - 当前有描述但不精确。例如 Solution Pro 的 `从需求到架构到实现方案` 太模糊
   - 改为：`输入：Living Spec → 输出：Implementation Plan（10 阶段串行管线，含质量门禁）`

8. **Legend 增加连接线样式说明**
   - 当前 legend 只解释了颜色编码，缺少对连接线的说明
   - 增加：实线 = 控制流、虚线 = 数据流、双向 = 读写

### 🟢 可选改

9. **考虑增加"跨层调用"的标注**
   - 例如 Investment 是否直接调用 TushareProvider（L1 data/）？如果是，应该有一条跨层连线

10. **增加一个简化的 "30 秒版" 缩略图**
    - 当前全景图信息量大，可以考虑在顶部放一个极简版（只有 L0→L1→L2 三个方块 + 两个箭头），作为心智模型的入口

11. **文件类型颜色编码（.py/.md/.yaml/.json）在架构图中的价值有限**
    - 颜色已经用于区分层级和文件类型，双重编码增加了认知负担
    - 如果删掉文件清单（建议 #1），这个颜色编码自然也不需要了

## 理想架构图应该长什么样？

我心目中的 DeepFlow 架构图应该是**"三层 + 一条通信带"**的结构：

### 布局

```
┌─────────────────────────────────────────────────┐
│  L0 · OpenClaw 宿主层                            │
│  [Main Agent] ──spawn──▶ [sessions_runtime]     │
└───────────────────┬─────────────────────────────┘
                    │ 控制流: sessions_spawn + exec
                    ▼
┌─────────────────────────────────────────────────┐
│  L1 · DeepFlow 核心引擎                          │
│                                                  │
│  ┌──────────┐  ┌──────────┐  ┌───────────────┐  │
│  │ 统一入口  │  │ Blackbox │  │ Cage + Prompt │  │
│  │ 编排调度  │  │  总线    │  │   注册中心     │  │
│  └──────────┘  └────┬─────┘  └───────────────┘  │
│                     │                            │
└─────────────────────┼────────────────────────────┘
                      │  ◀══ Blackboard 协议层（JSON 文件读写）══▶
                      ▼
┌─────────────────────────────────────────────────┐
│  L2 · Domain 领域模块                            │
│                                                  │
│  ┌─────────────────┐  ┌─────────────────┐        │
│  │  Spec Pro       │  │  Solution Pro   │  ← 核心│
│  │  需求→Living Spec│  │  Living Spec→Plan│        │
│  └─────────────────┘  └─────────────────┘        │
│                                                  │
│  ┌─────────────┐  ┌─────────────┐                │
│  │ Investment  │  │ Research    │  ← 附加        │
│  └─────────────┘  └─────────────┘                │
└─────────────────────────────────────────────────┘
```

### 核心原则

1. **信息密度法则**：架构图的每个元素应该在 3 秒内被理解。如果一个元素需要读文件名才能理解，它就不应该出现在架构图上。

2. **三层职责清晰**：
   - L0 = "谁在跑"（宿主环境）
   - L1 = "怎么跑"（框架机制：入口、总线、契约）
   - L2 = "跑什么"（业务领域）

3. **通信带突出**：Blackboard 是整个系统最关键的创新点（Agent 间唯一状态共享），它应该是**最显眼的元素之一**，而不是藏在 L3 的一个卡片里。

4. **视觉权重 = 架构权重**：核心模块大、亮、突出；附加模块小、暗、靠后。不要给 15K 行的模块和 2.7K 行的模块同样大的卡片。

5. **数据流可视化**：用箭头方向、线型（实线/虚线）、标签说明"什么数据从哪到哪"。架构图不是静态快照，是动态系统的冻结帧。

6. **文件名不出现在架构图**：架构图是"地图"，文件清单是"地籍册"。两者用途不同，不应混用。如果需要文件级别的细节，应该是架构图下方的"详细附录"或链接。

> **一句话总结**：当前架构图更像一份**项目目录报告**，而不是一份**系统架构图**。做减法比做加法重要——去掉 80% 的文件名，架构图的价值反而会提升 300%。
