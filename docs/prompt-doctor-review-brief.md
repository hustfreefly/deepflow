# Prompt Doctor Skill 评审材料

## 评审背景

**来源**：Solution Pro V31-V4.0 的 prompt 设计问题复盘

**核心发现**：当前 prompt 设计缺少维度分层，导致：
- V31-V35 崩溃本质是"流程跑不通"（Agent 不知道何时结束、状态如何流转）
- V4.0 修复方向正确（简化状态机、读文件模式），但仍缺少显式的"完成条件"定义

---

## 核心观点：Prompt 设计两层架构

### 第一层：流程可执行性（0→1）
**目标**：确保 Agent 知道任务边界、知道如何按 prompt 结束任务

**必须包含**：
1. **任务边界**：你负责什么、不负责什么
2. **状态流转**：当前状态 → 触发条件 → 下一状态
3. **完成条件**：什么情况下算完成、什么情况下算失败
4. **退出机制**：遇到问题时如何优雅退出（而不是无限循环）

**示例结构**：
```
你是 Solution Pro Orchestrator。

## 任务边界
- 负责：从 Living Spec 生成 Acceptance Criteria
- 不负责：修改 Living Spec、执行测试

## 状态流转
1. 读取 Living Spec → 如果成功 → 进入 Phase 1
2. Phase 1 完成 → 如果质量达标 → 进入 Phase 2
3. Phase 2 完成 → 写入 artifacts/ → 结束

## 完成条件
- 成功：所有 AC 写入 artifacts/acceptance_criteria.md
- 失败：Phase 1 质量不达标 → 输出失败原因 → 结束

## 退出机制
- 如果 Living Spec 读取失败 → 立即结束，输出错误信息
- 如果 Phase 1 重试 3 次仍失败 → 结束，输出失败原因
```

### 第二层：过程质量（1→N）
**目标**：确保每个阶段的输出质量符合预期

**必须包含**：
1. **质量预期**：输出应该达到什么标准
2. **验证标准**：如何判断输出是否合格
3. **示例**：好的输出长什么样、坏的输出长什么样

---

## 当前 Solution Pro 现状分析

### 第一层（流程可执行性）— 核心问题

**V31-V35 的崩溃**：
- Orchestrator 不知道"Research 完成后应该继续 Step 3/4/5"
- 状态流转逻辑在 prompt 中不清晰
- Agent 不知道"何时算完成"

**V4.0 的修复**：
- 移除 Step 4/5 后置验证（简化状态机 13→10 状态）
- 改为读文件模式（避免 prompt 灌入）

**但仍然缺失**：
- 没有显式的"完成条件"定义
- 状态流转的触发条件不够清晰
- 缺少明确的退出机制

### 第二层（过程质量）— 已有但需优化

**V4.0 的 14 prompt 体系**：
- Phase 1 规格审计 9 个 prompt
- Phase 2 AC 生成 5 个 prompt

**问题**：
- 这些 prompt 的前提是"流程能跑通"
- 如果第一层有问题，第二层再精细也没用

## 待评审问题

### 问题 1：两层分层是否正确？
- 这个分层是否覆盖了 prompt 设计的所有关键维度？
- 是否还有其他维度被遗漏？
- 两层之间的优先级关系是否正确（先 0→1，再 1→N）？

### 问题 2：第一层（流程可执行性）的设计原则
- 除了任务边界、状态流转、完成条件、退出机制，还需要什么？
- 如何确保 Agent 真正"理解"这些约束（而不是被忽略）？
- 是否有反模式需要避免？

### 问题 3：第二层（过程质量）的设计原则
- 质量预期如何量化或具体化？
- 验证标准应该是代码层（Pydantic）还是 prompt 层？
- 如何平衡"质量保障"和"执行效率"？

### 问题 4：Skill 设计
- Prompt Doctor Skill 应该包含什么内容？
- 输入是什么？输出是什么？
- 如何与现有的 AgentDryRun Skill（静态分析）和 Doctor Skill（动态分析）区分？
