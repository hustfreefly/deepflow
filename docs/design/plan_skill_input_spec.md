# Plan Skill 需求规格

> 本文档定义 Plan Skill 的用户需求、平台约束和验收标准。
> 版本：V1.0 | 日期：2026-06-25

---

## 1. 一句话目标

**在执行重要任务前，强制走"方案→评审→执行"闭环，确保高质量交付。**

---

## 2. 用户画像

- **用户**：姬忠礼（单人自用）
- **沟通风格**：高信号密度，直接给结论，不要绕弯子
- **质量要求**：验证失败 = 失败，不是"基本完成"
- **耐心天花板**：快速预览 → 初稿 → 完整报告，管理耐心

---

## 3. 核心需求

### 3.1 三种执行模式

| 模式 | 适用场景 | 专家数量 | 迭代轮数 | 预计耗时 |
|------|---------|---------|---------|---------|
| **Lite** | 简单修改、小功能 | 1 个 | 1 轮 | 5-10 分钟 |
| **Standard** ⭐ | 中等复杂度任务 | 2-3 个 | 1 轮 | 15-25 分钟 |
| **Pro** | 架构设计、重要决策 | 2-3 个/轮 | 5-10 轮 | 30-90 分钟 |

> ⭐ Standard 是主力模式，80% 的任务用 Standard 就够了。

### 3.2 模式选择

- **默认行为**：用户说 `/plan` 后，模型自动判断任务复杂度，选择合适模式
- **告知用户**（一行，不阻塞）：
  ```
  📋 Plan mode: Standard（理由：中等复杂度任务，涉及多文件修改）
  ```
- **Override**：用户可随时说 "用 Pro" 或 "用 Lite" 来覆盖
- **显式触发**：`/plan lite`、`/plan standard`、`/plan pro` 强制指定模式

### 3.3 核心流程（6 步闭环）

```
0. 任务澄清 → 1. 制定方案 → 2. 专家评审 → 3. 自主判断 → 4. 契约执行 → 5. 汇报结果
```

**Step 0: 任务澄清（必选，所有模式）**
- 做什么：用一句话重述任务目标
- 约束是什么：时间、依赖、风险
- 成功标准：怎么算"做完了"
- Lite 模式可以一句话带过，Standard/Pro 需要显式拆解
- 如果有多种理解 → 列出选项，让用户选择

### 3.4 Pro 模式特殊要求

- **迭代轮数**：5-10 轮（最少 5 轮确保充分迭代，最多 10 轮防止无限循环）
- **收敛标准**：问题闭环（不是"改动少了就收敛"，而是"所有问题都有闭环"）
  - ✅ 已修复：采纳意见，方案已修改
  - ❌ 已拒绝：不采纳，但给出理由
  - 📋 记录 TODO：好建议但超出本次范围
  - **收敛条件**：所有专家问题都有明确状态（无"未响应"问题）
- **提前收敛**：第 N 轮（N≥5）所有问题已闭环，直接收敛
- **强制收敛**：第 10 轮后，剩余问题强制标记为"已拒绝"或"记录 TODO"

### 3.5 Lite 模式特殊要求

- **必须用不同模型评审**：专家评审必须使用与主模型不同的 LLM，避免同一模型自我验证
- **评审 prompt 必须包含**：
  - 原始任务描述
  - 模型选择理由
  - 方案本身
  - 明确的评审 checklist（不能只说"请评审"）

### 3.6 专家选择

- **精准匹配**：与任务直接相关的领域专家
- **禁止凑数**：与任务无关的专家
- **禁止过度设计**：单人自用场景，不需要安全/合规/多租户专家

**示例**：
- 代码重构 → 架构专家、代码质量专家
- UI/交互 → UX专家、前端专家
- 自用工具 → 实用主义开发者

### 3.7 自主判断

- **专家意见不是圣旨**：主 Agent 必须自主判断，不无条件采纳
- **判断三标准**：
  1. **目标对齐**：是否直接服务于本次任务目标？
  2. **范围匹配**：是否在 YAGNI 范围内？
  3. **成本合理**：改动成本 vs 收益是否合理？
- **处理方式**：
  - 直接服务于任务目标 → 采纳，列入修改清单
  - 过度设计/超出范围 → 不采纳，记录原因
  - 好建议但不在本次范围 → 记录为 TODO，不修改当前方案

### 3.8 契约笼子执行

- 关键数据结构用 Pydantic schema 验证
- 写入前用 gate 函数拦截格式错误
- 执行后验证（测试通过 = 完成）

### 3.9 汇报模板（固定格式）

```markdown
## ✅ 任务完成报告

### 做了什么
- [具体改动列表]

### 验证结果
- [测试/门控通过情况]

### 遗留问题
- [如有]

### 采纳的专家意见
- [采纳了什么，为什么]

### 未采纳的专家意见
- [未采纳什么，为什么]
```

## 4. 可靠性需求

### 4.1 问题场景

| 问题 | 影响 |
|------|------|
| 子 Agent 超时/卡死 | 整个流程阻塞 |
| sessions_yield 后不唤醒 | 流程中断 |
| Pro 模式多轮迭代中断 | 前功尽弃 |
| 部分完成（3 个中 2 个完成 1 个卡死） | 整个流程阻塞 |

### 4.2 可靠性要求

| 要求 | 说明 |
|------|------|
| **超时保护** | 子 Agent 必须设置超时（runTimeoutSeconds），超时自动终止 |
| **部分完成容忍** | ≥2/3 完成就继续，不要求全部成功 |
| **状态持久化** | Pro 模式每轮写入状态文件，支持崩溃恢复 |
| **Watchdog 兜底** | Pro 模式每轮创建定时唤醒，防止流程卡死 |
| **执行失败回退** | 执行阶段发现方案不可行 → 回到任务澄清，最多回退 1 次 |

## 5. 平台约束

### 5.1 OpenClaw 平台能力

| 原语 | 说明 |
|------|------|
| `sessions_spawn(mode="run", runTimeoutSeconds=N)` | 启动子 Agent（后台运行，超时自动终止） |
| `sessions_yield()` | 等待子 Agent 完成事件（push-based，不轮询） |
| `subagents(action="list")` | 查看子 Agent 状态 |
| `cron(action="add", schedule.kind="at")` | 定时唤醒（用于 watchdog） |
| `sessions_send(sessionKey, message)` | 跨会话发送消息 |

### 5.2 嵌套 Spawn 支持

**配置**：`agents.defaults.subagents.maxSpawnDepth = 2`

**支持链路**：
```
主 Agent（depth 0）
  └── 子 Agent（depth 1）
        └── 孙 Agent（depth 2）
```

**含义**：子 Agent 完全可以再 spawn 子 Agent。这是 OpenClaw 原生支持的能力。

### 5.3 并发限制

| 配置项 | 当前值 | 说明 |
|--------|--------|------|
| `maxConcurrent` | 20 | 最大并发子 Agent 数 |
| `maxSpawnDepth` | 2 | 最大嵌套深度 |
| `archiveAfterMinutes` | 60 | 完成后归档时间 |

### 5.4 模型配置

| 配置项 | 当前值 | 说明 |
|--------|--------|------|
| 主模型 | `bailian/qwen3.7-plus` | 当前会话主模型 |
| 可用模型 | `kimi/qwen-max`, `bailian2/qwen3.7-max` 等 | 可用于 Lite 模式差异化评审 |

## 6. 适用场景

| 场景 | 示例 |
|------|------|
| ✅ 新功能设计 | 添加搜索功能、重构认证模块 |
| ✅ 架构重构 | 从单体拆分为微服务 |
| ✅ 重要文档编写 | 系统设计文档、API 规范 |
| ✅ 用户明确要求 | `/plan` 触发 |
| ❌ 低风险操作 | 版本号对齐、格式修复 |
| ❌ 紧急修复 | 先修后报，不走流程 |
| ❌ 简单查询 | 直接回答，不出方案 |

---

## 7. 验收标准

| 标准 | 验证方式 |
|------|---------|
| ✅ Lite 模式 5-10 分钟完成 | 实测计时 |
| ✅ Standard 模式 15-25 分钟完成 | 实测计时 |
| ✅ Pro 模式 30-90 分钟完成，5-10 轮迭代 | 实测计时 |
| ✅ 子 Agent 超时/卡死不阻塞流程 | 故障注入测试 |
| ✅ 崩溃恢复（state.json 读回继续） | 手动中断 + 重启测试 |
| ✅ 收敛标准明确（问题闭环） | 检查 state.json 中所有问题状态 |
| ✅ 汇报模板完整 | 检查输出格式 |
| ✅ 专家精准匹配（无凑数） | 检查 spawn 的专家类型 |

---

## 8. 明确禁止

| 禁止项 | 原因 |
|--------|------|
| ❌ 每步确认 | 全自动到结果，不要问"是否继续" |
| ❌ 过度设计型专家 | 单人自用，不需要安全/合规/多租户专家 |
| ❌ 事前选择模式 | 增加摩擦，自动判断 + 事后告知 |
| ❌ 静默假设用户意图 | 有歧义就问，不要猜 |
