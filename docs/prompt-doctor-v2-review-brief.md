# Prompt Doctor Skill V2 评审材料

## 评审背景

### 问题发现
Solution Pro V31-V35 崩溃的根因分析发现：
- **Layer 1（流程可执行性）缺失**：Worker prompt 不知道何时完成、何时失败
- **修复方向错误**：初版设计是 Fail Fast（快速失败），但用户指出这降低了系统稳健性

### 用户反馈（关键）
> "你这个东西我看你修复东西就是说，让Worker他妈觉得一有问题，老子就自己报错就不干了，是不是？干一次之后觉得有问题，重试不了也不干了，这不就人为的让我 Solution Pro 不稳健了吗？"

**核心洞察**：
- ❌ 错误方向：Fail Fast（遇到问题就退出）
- ✅ 正确方向：**稳健性优先**（遇到问题尝试恢复，无法恢复时才报告）

---

## 当前 Prompt Doctor Skill（V1）的问题

### 设计原则错误
V1 的核心原则是"Fail Fast"：
- Worker 遇到问题 → 报错退出
- Module Agent 重试 1 次 → 失败就放弃

这恰恰**降低了系统稳健性**：
- Worker 一次失败就放弃 → 本来可以恢复的问题变成了系统失败
- Module Agent 只重试 1 次 → 瞬时故障也会导致整个流程失败

### 检查清单设计问题
V1 的检查清单关注"是否有退出机制"，但没有关注：
- 是否有**恢复策略**？
- 是否有**降级方案**？
- 是否有**智能重试**？

---

## V2 设计方向（待评审）

### 核心原则：稳健性优先

**Worker 层**：
- 遇到问题 → 尝试恢复（重试、降级、报告问题但继续）
- 只有"无法恢复"的问题才报错退出
- 报错时输出详细的失败原因，帮助上游决策

**Module Agent 层**：
- 有上限的重试（比如 3 次）
- 重试失败后，尝试降级方案（比如跳过非关键步骤）
- 只有"关键步骤失败"才报告失败

**Orchestrator 层**：
- 模块失败后，尝试从断点恢复
- 只有"无法恢复"才报告整体失败

### 分层恢复策略

| 层级 | 恢复策略 | 示例 |
|------|---------|------|
| Worker | 本地重试 + 降级 | 输入文件缺失 → 尝试从其他来源读取 |
| Module Agent | 重试 Worker + 降级 | Worker 失败 → 重试 3 次 → 跳过非关键 Worker |
| Orchestrator | 重试模块 + 断点恢复 | 模块失败 → 从 checkpoint 恢复 |

### 错误分类

| 错误类型 | 处理策略 |
|---------|---------|
| 瞬时故障（网络、超时）| 自动重试 |
| 可恢复错误（输入格式错误）| 尝试修复 + 重试 |
| 不可恢复错误（关键输入缺失）| 报告失败 + 详细原因 |

## 待评审问题

### 问题 1：核心原则是否正确？
- "稳健性优先"是否覆盖了所有关键维度？
- 是否还有其他维度被遗漏？
- 如何平衡"稳健性"和"执行效率"？

### 问题 2：分层恢复策略是否合理？
- Worker / Module Agent / Orchestrator 三层的职责划分是否清晰？
- 每层的恢复策略是否充分？
- 是否有反模式需要避免？

### 问题 3：错误分类是否正确？
- 瞬时故障 / 可恢复错误 / 不可恢复错误的分类是否合理？
- 每类错误的处理策略是否最优？
- 是否有其他错误类型被遗漏？

### 问题 4：检查清单设计
- V2 的检查清单应该包含什么？
- 如何确保"稳健性"被正确评估？
- 如何避免 V1 的"Fail Fast"陷阱？
