## 三、做得不好的

### 1. 4 个 WP"完成但未被识别"，累计空耗 ~26h 墙钟
- 工作实际早完成（cust_001 交付物 01:42、pdk_002 03:43、road_002 03:18、eda_002 校验 04:53）
- 但 `delivery_manifest.json` 直到修复期才写入（08:17 / 08:23 / 11:20 / 11:24）
- 卡 PACKAGING 达 **4.6~9.7h**
- 根因：LLM 写坏 `validation_result.json` → 无校验回退 PACKAGING → 无限循环

### 2. 状态双写漂移
- `batch_progress.json` 全部 DONE，但 27/28 个 WP 的 `delivery_state.json` 仍停在 PACKAGING
- 终态枚举混乱——eda_006=DONE、pdk_004=VALIDATED、team_001=COMPLETE 三种"完成"标签
- 任何读 delivery_state 的监控/工具都会误判项目仍在进行

### 3. 告警机制整体依赖 pulse 运行，而 pulse 依赖主 agent 手动跑
- `crontab` 为空、无 launchd 定时器，pulse 从未成为独立调度
- pulse 不跑 → zero_progress_count 不递增 → 一切告警静默失效

### 4. STALLED 判定把"有 spawn 动作"当"有进展"
- PACKAGING 卡死的 WP 每 30min 被 stale timeout 重派一次
- 每次都有 spawn 动作 → 计数永远归零 → **重派风暴直接压制告警**
- 07-29 实况铁证：21 个 WP 卡 PACKAGING 5h，`zero_progress_count=0`，无任何告警

### 5. 契约定义了但没在边界强制
- Pydantic model 存在，5 个 LLM 输出消费点却全是裸 `json.loads` + `dict.get()`
- 契约沦为了"文档"而非"闸门"

### 6. 异常处理无分类纪律
- 4 个核心文件 90 个 `except`，≥6 处裸 `except: pass/continue`
- 异常分类过粗与吞异常并存

### 7. 上帝类 + 薄状态层
- orchestrator.py 2698 行，16 处内联 json.load
- state_manager.py 只有 40 行——持久化关注点名义上被抽出来了，实际 orchestrator 又全部内联实现了一遍

### 8. M1 暴露了代码生成/复制粘贴未拦截
- `verify_package_output` 四次相同定义、第 4 次生效
- Python "last definition wins" 的静默陷阱，review 完全没拦住

### 9. 主 agent 救火式介入 3h 串行占用
- 08:22 发现 → 审计 → 三专家评审 → SafeJsonLoader 实现 → 部署 → 状态回填
- 全程串行到 ~11:24，期间 wave 4 调度停滞

### 10. Pulse 同步阻塞主 agent
- `orch.pulse()` 全量扫描 28 WP + spawn，30-60s/次
- 主 agent 直接调时用户消息被挂起
- 直接造成 PDK-003→EDA-006 之间 1.9h 空窗

## 四、暴露的问题

### 问题 1：交付物本身未被验证
- 复盘聚焦"管线缺陷"，但 28 个 WP 项目的**输出内容**是否完整、正确，没有任何证据
- MANIFEST 损坏 = 无法证明交付物完整性，却同时得出"28 项目完成"的结论
- **这个结论建立在不可信的状态上**

### 问题 2：损坏率没有度量
- 17 个缺陷 / 28 个项目 —— 这是"被发现"的数量，不是损坏率
- 损坏是第一批就发生，还是第 20 个才出现？没有时间线、没有损坏率基线
- 无法判断防御 vs 消除的成本取舍，也无法验证修复是否真的有效

### 问题 3：根本问题是生成端，不是解析端
- 为什么这么多 LLM 输出损坏？
- 没有强制结构化输出（裸 `json.loads` 说明生成侧只是 prompt 里写"输出 JSON"）
- 最常见的损坏原因没被排查：`max_tokens` 截断、流式拼接断连、输出混入 markdown 代码块
- 没有 validate-and-retry 生成循环

### 问题 4：检测延迟 = 元缺陷
- 缺陷跑完 28 个项目才暴露，说明管线"静默继续"是设计哲学
- 17 个缺陷里没有一个是监控/告警类缺陷，这本身就是最大的盲点

### 问题 5：没有测试策略
- 整个复盘零测试：没有复现 H1-H3 的最小用例、没有损坏样本库、没有回归测试
- 修复没有验证手段 = 修复本身无法验证

### 问题 6：三层盲区叠加导致 4 个 WP 卡 6h 无告警
1. Pulse 没有独立调度，不跑则一切告警失效
2. STALLED 把"重派动作"当"进展"，卡死被重派风暴持续压制
3. 没有任何 per-WP 停留时间监控

### 问题 7：状态一致性无保障
- `wp_runner` 写 `delivery_state.json`、`orchestrator` 写 `batch_progress.json`，双源**无对账**
- H2 重建后 batch_progress 重置而 delivery_state 保留 → 永久不一致

## 五、根因分析

### 一句话根因
**架构把状态文件当作"正确性由构造保证"（MD-First 中 JSON 是衍生品），而不是"任何时刻都可能损坏、必须显式声明降级行为"。衍生品 ≠ 可丢弃品——写路径永远不会失败的假设，让所有读取点失去了防御设计。**

### 根因模式
| 模式 | 描述 | 涉及缺陷 |
|------|------|----------|
| A | LLM 输出无校验直接消费 | H1, M2, M3, M5, M8 |
| B | 异常吞掉后状态丢失 | H2, M6 |
| C | 无限重试无上限 | H3 |
| D | 异常分类过粗 | M7, L2 |

### 为什么设计阶段没发现
- 设计文档定义了领域不变量，但**没有定义运行时边界不变量**
- 故障注入不在设计词汇表里，corrupt 属于对抗性输入，设计评审不会自然枚举

## 六、改进建议

### P0（立即执行）

#### 1. 调度与监控独立于主 agent
- 把 pulse 从"主 agent 手动 exec"迁移到 `launchd`/`crontab` 定时任务
- 主 agent 只做 `check`
- 这同时解决"阻塞主 agent"和"pulse 不跑告警失效"两个问题
- pulse 每次执行写 `last_pulse_at` 时间戳

#### 2. STALLED 判定口径修正
- `n_spawn_actions == 0` 改为"本轮无新完成（completed+terminal_failed 未变）且无新产出文件"
- 重派不等于进展——重派同一 action 不允许归零计数

#### 3. per-WP 停留时间（dwell time）监控
- 这是本次"4 个 WP 卡 6h 无告警"的直接解药
- 每次 pulse 计算每个 WP 当前 phase 的停留时长
- 超阈值告警（PACKAGING >2h WARN、>6h CRITICAL）

#### 4. 单一状态源 + 终态枚举统一
- `batch_progress` 与 `delivery_state` 二选一为主，另一为派生
- 统一终态为 `DONE`
- pulse 内加 reconciliation diff，两文件不一致直接告警

### P1（短期执行）

#### 5. 告警推送通道
- alert 从 report 字段升级为可推送事件
- pulse_cli 在 `alerts` 非空时直接发送飞书消息
- 冷却 30min 已有，防轰炸

#### 6. 边界强制层制度化
- 所有状态/LLM 输出读取必须走 `SafeJsonLoader + Pydantic`
- 新增读取点写代码前先过这条规则
- 把它写进 SKILL.md/AGENTS.md，而不是靠自觉

#### 7. 显式降级策略声明
- 每个状态读取点必须声明"不可读时行为 X"
- 禁止隐式 fallback
- 降级路径与主路径同等 review 权重

#### 8. 异常三分类纪律
- 瞬态（OSError → 重试）、逻辑（ValidationError → 判死）、损坏（隔离 + 备份 + 重建 + 告警）
- `except Exception` 裸捕获应在代码评审中直接打回

#### 9. 熔断 + 人工恢复入口
- 实现 Phase D 腐坏率熔断（单周期 ≥3 WP 损坏 → 停止 dispatch + CRITICAL 告警）
- `pulse_cli` 增加 `resume`/`unblock` 子命令作为熔断后人工恢复入口

#### 10. 状态持久化收拢
- 把 load/save/rebuild/quarantine 全部收进 StateManager
- orchestrator 只做调度决策
- 先解决"状态归谁管"再谈拆类

### P2（中期执行）

#### 11. 上帝类按职责分解
- orchestrator 2698 行拆为调度决策 / 状态持久化 / 告警三块
- 否则状态机不变量无人能整体把握

#### 12. CI 静态护栏
- 禁止裸 `except`、禁止 except 内 `continue/pass`
- 边界 `json.loads` 必须过 loader
- 重复定义检测（AST 或 pylint duplicate-code）

#### 13. 故障注入测试矩阵
- 每个状态文件一个"损坏→断言降级行为"测试
- 一个不变量测试（"pulse tick 后所有状态文件仍可解析"）
- 测试清单与状态文件清单一一对应，缺一个算未完成

#### 14. 卡死自愈而非告警
- H3 修复（retry counter 上限）必须配"终态回填"
- manifest 缺失但 `final_deliverable` 已存在时，让 Package Agent 幂等重写而不是无限回退
- 修复后 sweep 应把 DONE 写回 delivery_state

#### 15. 元数据与数据分离
- `_meta` 移出 WP map（单独文件或 `_` 前缀过滤约定）
- 避免"29 条记录"类误判反复出现

#### 16. 事故 runbook 预置
- 把本次 3h 救火路径固化为脚本化命令
- 下次 5 分钟解决

#### 17. 异步 Pulse 落地
- `--async`（Popen 后台）或先落地 `--max-wps 5` 增量模式
- 2h 工作量，立即可消除主 agent 30-60s 阻塞

## 七、不愿面对但必须面对的

### 1. 28 个交付物可能不可信

- 团队应该重新验证全部 28 个输出，而不是合成 MANIFEST 假装无事
- 欺骗性最小的问题是："这 28 份交付给客户的东西，哪些是完好的？"—— 无人能回答

### 2. 这个复盘定义错了问题
- 它被命名为"防御性缺陷"，实际是"**生成不可靠 + 无验证 + 无告警**"三件套
- 命名决定修复方向：叫"防御缺陷"就修防御，叫"生成质量"就得动 prompt/模型/结构化输出

### 3. 可能全部白修
- 如果根因是 prompt/模型选型，Phase A-D 的 13h 是症状转移
- 先花 30 分钟统计损坏率、收集损坏样本、验证是否为截断问题 —— 这比 13h 防御便宜得多，且决定一切

### 4. 没有测试的修复 = 自欺完成
- AGENTS 规则：证据 = 完成
- 修复前后必须有可对比的损坏率指标，否则"修复完成"只是宣称

## 八、总结

### 核心教训
1. **衍生品 ≠ 可丢弃品**：JSON 是 MD 的衍生品，但写路径永远不会失败的假设是错的
2. **契约必须强制**：Pydantic model 存在不等于在边界强制
3. **告警必须独立**：告警机制不能依赖被监控对象
4. **重派 ≠ 进展**：STALLED 判定必须区分"有动作"和"有产出"
5. **生成端是根因**：防御是症状管理，消除损坏源才是根治

### 最值钱的产出
- 17 个缺陷的系统化发现
- SafeJsonLoader 的设计与实现
- 三专家交叉评审的流程验证
- 完整的事故处理留痕

3. **P1**：边界强制层制度化 + 显式降级策略 + 异常三分类（6h）
4. **P2**：CI 静态护栏 + 故障注入测试矩阵（4h）
