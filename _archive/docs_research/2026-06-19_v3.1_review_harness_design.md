# V3.1 评审：Harness 设计合理性

> **评审日期**: 2026-06-19
> **评审视角**: 信息架构师（Information Architect）
> **评审对象**: Ship Pro V3.1 修复方案第六节 — Harness 四维门控设计
> **参照系**: Solution Pro Harness V3（harness_v3.md + harness_scorer.py）+ 真实管线质量分析

---

## 评审结论：PASS_WITH_CONCERNS

**总体评价**：Harness 的设计理念正确——在每个 Agent 后设置确定性 Gate 做快速拦截，用 Reviewer 做语义审核，用 Final Eval 做全量校验。三层防线比 V3 的"最后才查"有本质进步。但存在 3 个设计缺陷需要修复后才能达到预期效果。

## 关键发现

### 发现 1：coding_readiness 权重 40% 但 Gate 中几乎无法 Code-Based 检查 🔴

**问题**：三维评分中 `coding_readiness` 占 40%（与 information_density 并列最高），但修复方案明确标注其评估方式为 **LLM-Based**。而 Gate 的核心价值是 **快速确定性检查（<2s）**——Gate 中的 Code-Based 检查实际上只覆盖了 information_density（空字段率）和 traceability（映射链），coding_readiness 在 Gate 层几乎没有确定性检查项。

**矛盾**：真实管线暴露的核心问题是"字段全空"——这是确定性的、可 Code-Based 检查的。但 Harness 设计把 coding_readiness 定义为"AI Agent 拿到后能直接干活吗？"这个语义问题，交给了 LLM Reviewer。

**风险**：Gate 的 Code-Based 检查能发现"budget 为 null"，但无法发现"budget 填了但值不合理"（比如给一个简单配置 WP 分配 100k tokens）。后者才是 coding_readiness 的核心，但 Gate 不检查它。

**建议**：
- 将 coding_readiness 拆为两层：
  - **coding_readiness_structural**（Code-Based）：核心字段非空 + 值类型正确 + 在合理范围内（budget > 0, complexity ∈ {low,medium,high}）
  - **coding_readiness_semantic**（LLM-Based）：值是否合理、AI Agent 能否直接开工
- Gate 只做 structural 层，Reviewer 做 semantic 层

### 发现 2：阈值设计对 Specifier Gate 过于宽松 🔴

**问题**：
```
PASS: 空字段率 = 0% AND AC评分 ≥ 70 AND Schema 合规
CONDITIONAL: 空字段率 < 10% AND AC评分 ≥ 60
FAIL: 空字段率 > 10% OR AC评分 < 60
```

CONDITIONAL 允许空字段率达到 9.9%。以 7 个 WP、每个 WP 8 个核心字段计算，总共 56 个字段——9.9% 意味着可以有 5 个字段为空仍通过。

**真实管线教训**：V3 的问题是 **56 个字段全空**（100% 空字段率）。如果阈值设为 CONDITIONAL < 10%，那从 100% 到 9.9% 的修复跨度太大，实际上意味着"几乎全部修复才能过 CONDITIONAL"。

**更深层问题**：CONDITIONAL 通过后的处理逻辑未定义。CONDITIONAL 是"带着问题继续"还是"需要修复但不能阻塞"？修复方案中没有说明 CONDITIONAL 的后续动作。

**建议**：
- Specifier Gate 的阈值应该更严格：
  ```
  PASS: 空字段率 = 0% AND AC评分 ≥ 70 AND Schema 合规
  FAIL: 空字段率 > 0% OR AC评分 < 60 OR Schema 不合规
  ```
  即：**Specifier Gate 没有 CONDITIONAL**。核心字段有空 = FAIL，没有中间地带。
- 或者保留 CONDITIONAL 但将阈值降到 < 3%（即 56 个字段中最多 1 个可为空，且必须是非关键字段）

### 发现 3：Gate 评分公式对所有检查项等权处理 ⚠️

**问题**：
```python
score = sum(checks.values()) / len(checks)
```

7 个检查项等权。但 `budget 为 null`（AI Agent 无法选模型）和 `字段命名用了 wp_id 而不是 id`（纯格式问题）的严重性完全不同。等权处理意味着：如果 Schema 合规但 budget 全空，score = 6/7 = 0.857 ≥ 0.8 → PASS。这显然不合理。

**建议**：
- 引入分级权重：
  - **Critical checks**（权重 3x）：budget/complexity/outputs/requirements 非空
  - **Major checks**（权重 2x）：Schema 合规、AC 评分
  - **Minor checks**（权重 1x）：字段命名、格式
- 或者引入"一票否决"机制：任何 Critical check 失败 = 直接 FAIL，不论总分

### 发现 4：Architect Gate 的"实现蓝图"检查只验存在性，不验质量 ⚠️

**问题**：Gate 1 的检查项：
```yaml
- implementation_blueprint 存在且非空
- project_structure.directories 至少 1 项
- wp_file_mapping 存在
```

这些只检查"有没有"，不检查"够不够好"。如果 Architect 输出 `directories: ["src/"]`（只有 1 个目录）也能通过。但这对下游 Specifier 毫无帮助。

**建议**：
- 增加质量阈值：
  ```
  - project_structure.directories 数量 ≥ 3（至少区分核心模块/前端/基础设施）
  - wp_file_mapping 覆盖率 = 100%（每个 WP 都有对应的文件映射）
  - key_interfaces 至少 1 项（有 API 定义）
  ```

### 发现 5：缺少跨 WP 一致性 Gate ⚠️

**问题**：4 个 Gate 都是"单 Agent 输出检查"——每个 Gate 只检查当前 Agent 的输出质量。但真实管线中有一类问题是**跨 WP 一致性**的：
- WP-001 的 outputs 包含 `src/gateway/`，WP-003 的 context_files 引用 `src/gateway/router.go`——这两个信息是否一致？
- 依赖图中的 WP-001 → WP-002 是否意味着 WP-002 的 context_files 应包含 WP-001 的 outputs？

这类一致性检查在 Gate 2（Decomposer）和 Gate 3（Specifier）中都没有覆盖。

**建议**：在 Gate 3（Specifier）中增加跨 WP 引用一致性检查：
```python
"cross_wp_consistency": all(
    wp["context_files"] is subset of upstream_wp["outputs"]
    for wp in wps if wp has dependencies
)
```

### 发现 6：与 Solution Pro Harness 的差异是合理的 ✅

**分析**：Solution Pro 的 4 维评分（completeness/necessity/alignment/global_impact）评估的是"方案对人类决策者的质量"，Ship Pro 的 3 维评分（information_density/coding_readiness/traceability）评估的是"产出对 AI Coding Agent 的可执行性"。这是两个不同的消费场景，维度设计不同是合理的。

**具体差异分析**：
| Solution Pro 维度 | Ship Pro 对应 | 是否覆盖 |
|---|---|---|
| completeness（完整性） | information_density（信息密度） | ✅ 覆盖角度不同但互补 |
| necessity（必要性） | — | ⚠️ 未显式覆盖，但 Gate 的 Schema 合规检查隐含了"不多不少" |
| alignment（目标一致性） | traceability（可追溯性） | ✅ 可追溯性是 alignment 的可量化版本 |
| global_impact（全局影响） | — | ⚠️ 未覆盖，但 Ship Pro 不涉及"全局影响"决策 |

**结论**：3 维对 Ship Pro 的场景是足够的。necessity 和 global_impact 对"AI Coding 可执行性"不是关键维度。

## 具体建议

### 建议 1：Specifier Gate 取消 CONDITIONAL，改为二元判定 🔴 P0

```yaml
# 修改前
PASS: 空字段率 = 0% AND AC评分 ≥ 70 AND Schema 合规
CONDITIONAL: 空字段率 < 10% AND AC评分 ≥ 60
FAIL: 空字段率 > 10% OR AC评分 < 60

# 修改后
PASS: 空字段率 = 0% AND AC评分 ≥ 70 AND Schema 合规
FAIL: 空字段率 > 0% OR AC评分 < 60 OR Schema 不合规
```

**理由**：真实管线的教训是"全空也能通过 Reviewer"。对 AI Coding 关键字段，有空 = 不可执行 = 必须返工。没有"部分可执行"的中间状态。

### 建议 2：Gate 检查项引入分级权重 🔴 P0

```python
CRITICAL_CHECKS = ["budget_filled", "complexity_filled", "outputs_non_empty", "requirements_non_empty"]
MAJOR_CHECKS = ["schema_compliant", "ac_score_70"]
MINOR_CHECKS = ["field_naming_correct"]

def gate_specifier(specs):
    checks = run_all_checks(specs)
    critical_pass = all(checks[c] for c in CRITICAL_CHECKS)
    major_score = sum(checks[c] for c in MAJOR_CHECKS) / len(MAJOR_CHECKS)
    minor_score = sum(checks[c] for c in MINOR_CHECKS) / len(MINOR_CHECKS)
    
    if not critical_pass:
        return {"passed": False, "score": 0, "reason": "Critical fields empty"}
    
    weighted_score = major_score * 0.8 + minor_score * 0.2
    return {"passed": weighted_score >= 0.8, "score": weighted_score}
```

### 建议 3：coding_readiness 拆为 structural + semantic 两层 🟠 P1

Gate 只做 structural（确定性、<1s）：
- 字段非空
- 值类型正确（complexity ∈ {low,medium,high}）
- 值在合理范围（budget > 0 且 < 1M tokens）

Reviewer 做 semantic（LLM 判断、~30s）：
- budget 估算是否与 AC 数量/复杂度匹配
- context_files 是否覆盖了 AC 涉及的代码区域
- AI Agent 能否不依赖额外信息开工

### 建议 4：Architect Gate 增加实现蓝图质量检查 🟠 P1

```yaml
# 新增检查项
- project_structure.directories 数量 ≥ 3
- wp_file_mapping 覆盖所有 WP（覆盖率 = 100%）
- key_interfaces 至少包含 1 个 API 端点定义
- data_models 至少包含核心实体
```

### 建议 5：定义 CONDITIONAL 的后续动作 🟡 P2

当前修复方案中 CONDITIONAL 通过后的动作未定义。建议：
- CONDITIONAL → 继续到下一个 Agent，但在最终 Reviewer 阶段标记为"需关注"
- 如果 Reviewer 也给出 CONDITIONAL → 自动触发回退到对应 Gate 修复

### 建议 6：反馈轮次设计合理，无需修改 ✅

Gate 最多 2 轮、Reviewer 最多 5 轮的设计合理：
- Gate 是确定性检查，2 轮足够（如果 2 轮都过不了，说明 Agent prompt 有根本问题，不是靠多轮能修的）
- Reviewer 是语义审核，5 轮给予足够空间做渐进式质量提升
- 总计最多 2+2+2+2+5+2 = 15 轮，对 30-60 分钟的管线来说可接受

## 与 Solution Pro Harness 的关键差异总结

| 维度 | Solution Pro | Ship Pro V3.1 | 评价 |
|------|-------------|---------------|:---:|
| 评分维度 | 4 维 | 3 维 | ✅ 合理（不同消费场景） |
| 决策层级 | 5 级（PASS → BLOCK） | 3 级（PASS/CONDITIONAL/FAIL） | ⚠️ 3 级够用但 CONDITIONAL 定义不清 |
| 阈值 | PASS ≥ 0.85 | PASS ≥ 0.8 | ✅ 略松但可接受 |
| 特殊规则 | alignment < 0.6 → 自动 CRITICAL | 无 | ⚠️ 建议增加"关键字段空 → 自动 FAIL" |
| 评分器 | 统一 Python 评分器 | 分散在各 Gate 函数中 | ⚠️ 建议统一为 harness_scorer_ship.py |
| 全局理解检查 | frozen_spec.executive_summary | 无 | ✅ 合理（Ship Pro 不需要"理解目标"，只需检查"信息完整"） |

## 总结

Harness 设计的**架构方向正确**：Gate 做快速确定性拦截，Reviewer 做语义质量审核，Final Eval 做全量校验。三层防线解决了 V3 "问题到最后才发现"的核心痛点。

**需要修复的 3 个关键问题**：
1. Specifier Gate 的 CONDITIONAL 阈值过松——核心字段有空应该直接 FAIL
2. Gate 检查项等权处理不合理——需要引入 Critical/Major/Minor 分级
3. coding_readiness 在 Gate 层缺乏 Code-Based 检查项——需要拆为 structural + semantic

修复这 3 点后，Harness 设计可以達到预期效果：**问题在产生它的 Agent 处就被拦截，而不是到了 Reviewer 或 Final Eval 才发现。**
