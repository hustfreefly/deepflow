## 关键障碍

### 1. Architect Prompt 注意力稀释风险 🔴

**现状**：当前 `architect.md` 约 5000 tokens，包含：
- 4 种 Format 的提取规则
- 7 个提取维度（modules, dependencies, requirements, domain_details, sla, risks, hints）
- 2 个 Few-Shot 示例（占 ~40% 篇幅）
- 自检清单

**问题**：新增 `implementation_blueprint` 会引入：
- project_structure（directories + key_files）
- key_interfaces
- data_models
- wp_file_mapping

预计新增 ~800 tokens。总计 ~5800 tokens，接近 LLM 的"注意力舒适区"上限。

**风险**：
- Architect 可能为了填 `implementation_blueprint` 而牺牲其他维度的提取质量
- Few-Shot 示例没有覆盖 `implementation_blueprint`，LLM 可能理解偏差

**建议**：
- 精简现有 Few-Shot 示例（2 个 → 1 个，或缩短示例长度）
- 将 `implementation_blueprint` 设为"尽力而为"（best-effort），不是硬性要求
- 或者：将 `implementation_blueprint` 拆成独立步骤（Phase 2），不在 Architect 阶段做

### 2. Harness 反馈闭环收敛性 🟠

**方案设定**：
- Gate FAIL → 反馈给 Agent → 最多 2 轮
- Reviewer FAIL → 反馈给 Agent → 最多 5 轮

**问题**：
- 2 轮够不够？如果 Gate 3（Specifier）反复 FAIL，说明问题不在 Specifier 输出，而在 Architect 输入质量
- "反馈给 Agent" 的具体机制是什么？`sessions_send` 还是重新启动？
- 如果 Agent 已经输出了最终结果并被 terminate，如何"反馈"？

**收敛性风险场景**：
```
Gate 3 FAIL: "budget 字段为空"
→ 反馈给 Specifier: "请填充 budget 字段"
→ Specifier 重跑，填充了 budget，但 complexity 又空了
→ Gate 3 FAIL: "complexity 字段为空"
→ 反馈给 Specifier: "请填充 complexity 字段"
→ Specifier 重跑，填充了 complexity，但 budget 又空了
→ 循环...
```

**建议**：
- 反馈消息必须包含**完整的 Gate 检查结果**，不只是"FAIL"
- 反馈消息必须明确指出**哪些字段为空**，而不是笼统说"字段不完整"
- 增加"升级机制"：2 轮 Gate FAIL 后，不是继续重试，而是上报给 Orchestrator 做决策（可能是 Architect 输入问题）

### 3. orchestrator.py 结构性改造 🟠

**现状**：当前 `orchestrator.py` 是"一次性准备"模式：
- 准备所有 Agent 的 task prompt
- 写入 `run_config.json`
- 主 Agent 按 `execution_order` 依次调用 `sessions_spawn`

**问题**：Harness 需要"动态编排"：
- 每个 Agent 输出后，立即运行 Gate 检查
- Gate FAIL → 重新 spawn 同一个 Agent（带反馈）
- Gate PASS → 才 spawn 下一个 Agent

**需要的改造**：
```python
# 当前逻辑（静态）
for agent in execution_order:
    spawn(agent)
    wait_for_completion()

# 需要的逻辑（动态）
for agent in execution_order:
    while True:
        spawn(agent, feedback=last_feedback)
        wait_for_completion()
        gate_result = run_gate(agent, output)
        if gate_result.passed:
            break
        elif retry_count < max_retries:
            last_feedback = gate_result.feedback
            retry_count += 1
        else:
            raise HarnessError(f"Gate {agent} failed after {max_retries} retries")
```

**影响范围**：
- `orchestrator.py` 需要新增 `run_gate()` 函数（调用 `eval_code_checks.py` 或专门的 gate 函数）
- 主 Agent 的调用逻辑也需要改造（从"按顺序 spawn"变成"spawn + gate + 条件 spawn"）
- `run_config.json` 需要新增 `gate_config` 字段（每个 Agent 的 gate 阈值、最大重试次数）

**工作量**：0.5-1 天（不是小修小补）

### 4. Specifier Prompt 重构的回归风险 🟠

**现状**：当前 `specifier.md` 经过 Phase 1-3 多轮打磨，包含：
- AC 质量 Rubric（四级量表）
- 防御性指令（禁止编造、禁止空泛、禁止遗漏）
- 自检规则（7 条）
- F3/F4 修复（风险缓解、context_files 约束）

**方案提议**：
- 改变执行顺序："先填表，后创作"
- 新增 Complexity 判定规则
- 新增 Schema 铁律
- 新增硬性 Gate

**风险**：
- 改变执行顺序可能导致 LLM 注意力分配变化，原本写好的 AC 质量可能下降
- "先填表"可能导致 LLM 为了填表而填表，字段有值但质量低
- 新增的"Schema 铁律"与现有的"防御性指令"可能有冲突

**建议**：
- 不要一次性重构，分两步：
  1. 先增加"硬性 Gate"（自检增强），不改执行顺序
  2. 观察一轮真实管线效果，再决定是否调整执行顺序

### 5. Gate 函数实现的复杂度 🟢

**方案提供的代码**：`gate_architect()` 和 `gate_specifier()` 约 50 行，逻辑清晰。

**可复用现有代码**：
- `check_schema_compliance()` — 已有
- `check_dependency_graph()` — 已有
- `score_all_acs()` — 已有
- `check_field_completeness()` — 已有

**需要新增的**：
- `gate_architect()` — ~30 行（检查 implementation_blueprint 存在性）
- `gate_specifier()` — ~40 行（检查字段非空 + 调用现有函数）
- `gate_decomposer()` — ~20 行（检查模块覆盖率）
- `gate_packager()` — ~20 行（调用现有 `run_all_checks()`）

**总计**：~110 行新代码 + 复用现有 ~200 行。复杂度可控。

## 执行建议

### 建议 1：分阶段实施，不要一次性全上

**Phase 3.6（P0，1 天）**：
- 实现 4 个 Gate 函数（纯函数，可独立测试）
- 扩展 `eval_code_checks.py`，新增 gate 入口
- 不修改 orchestrator.py，手动在 Gate FAIL 时反馈

**Phase 3.7（P0，1 天）**：
- 修改 orchestrator.py，支持动态编排
- 实现 Harness 反馈闭环（sessions_send 机制）
- 端到端测试

**Phase 3.8（P1，0.5 天）**：
- Architect 增强（implementation_blueprint）
- Specifier 增强（硬性 Gate）
- Reviewer 增强（AI Coding 可用性审核）

### 建议 2：Harness 反馈机制需要明确设计

当前方案只说"反馈给 Agent"，没有明确：
1. **反馈消息格式**：应该包含 Gate 检查的完整结果 + 具体哪些字段为空
2. **Agent 如何接收反馈**：`sessions_send` 还是重新启动（带 feedback context）？
3. **Agent 上下文保留**：如果重新启动，如何保留上一轮的输出作为参考？

**建议设计**：
```python
feedback_message = f"""
## Gate {gate_name} 检查结果：FAIL

### 未通过的检查项
{format_failed_checks(gate_result)}

### 你的上一轮输出（供参考）
```json
{json.dumps(last_output, indent=2)}
```

### 请修复以上问题后重新输出
"""
```

### 建议 3：Architect 的 implementation_blueprint 设为"尽力而为"

不要硬性要求 Architect 必须输出完整的 `implementation_blueprint`。理由：
1. Architect 的输入是 Solution Pro 的输出，不一定包含实现级细节
2. 强制要求可能导致 Architect 编造信息（违反"禁止编造"红线）
3. `wp_file_mapping` 等信息可能需要 Architect 做推理，超出"提取器"角色

**建议**：
- `implementation_blueprint` 存在 → Gate 加分
- `implementation_blueprint` 不存在 → Gate 不 FAIL，但标记为 `information_density: partial`
- 如果 `implementation_blueprint` 缺失，由 Specifier 从模块职责推导 outputs/context_files

### 建议 4：增加 Harness 的"升级机制"

当前方案：Gate FAIL → 重试 → 再 FAIL → 再重试 → 达到上限 → ???

**建议**：达到重试上限后，不是简单报错，而是：
1. 记录失败原因到 `harness_log.json`
2. 上报给主 Agent，由主 Agent 决策：
   - 跳过该 Gate，继续执行（带 warning）
   - 终止管线，输出部分结果
   - 人工介入
