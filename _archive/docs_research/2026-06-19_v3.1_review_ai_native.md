# V3.1 评审：AI Native 方法论

> **评审日期**: 2026-06-19
> **评审视角**: AI Native 方法论（理解力 > 规则穷举）
> **评审对象**: `ship_pro_v3.1_repair_plan.md` + 两份诊断报告
> **核心问题**: V3.1 修复方案是在用"穷举规则"解决问题吗？有没有退化成规则引擎？

---

## 评审结论：PASS_WITH_CONCERNS

V3.1 修复方案**整体方向正确**，但存在**明显的规则引擎退化倾向**。具体说：
- **Harness Gate 体系**（修复项 4）是 AI Native 的——用确定性代码做确定性检查 ✅
- **Specifier 的 complexity/requirements/outputs 修复**（修复项 2）退化为规则引擎——用 if-then 关键词匹配替代 LLM 理解 ❌
- **Architect 增强**（修复项 1）是 AI Native 的——让 LLM 输出"实现蓝图"是发挥理解力 ✅

**核心矛盾**：方案试图用"给 Specifier 塞更多规则"来解决"Specifier 填不满字段"的问题。这正是 AI Native 红线 R7（禁止 bloated prompt）和 R6（确定性任务用代码，语义任务用 LLM）的双重违反。

---

## AI Native 浓度分析

| 修复项 | AI Native 浓度 | 退化风险 | 建议 |
|--------|:---:|:---:|------|
| **修复项 1: Architect 实现蓝图** | 🟢 高 | 低 | 让 LLM 输出结构化蓝图是正确做法。LLM 理解需求→输出实现细节，这是理解力的体现 |
| **修复项 2: Specifier complexity 判定规则** | 🔴 低 | **高** | if-then 规则（"≥3组件→complex"）是典型规则引擎。LLM 完全能"理解"一个 WP 的复杂度 |
| **修复项 2: Specifier requirements 关键词匹配** | 🔴 极低 | **极高** | 关键词匹配表（"CDN,DNS→WP-001"）是 2020 年的 NLP 做法。LLM 能直接理解 REQ 和 WP 的语义关联 |
| **修复项 2: Specifier outputs 推导模板** | 🟡 中 | 中 | 模块类型→文件路径映射表是硬编码。但 Greenfield 场景下 LLM 确实需要一些锚点来推导 |
| **修复项 2: 执行顺序重排（先填表后创作）** | 🟢 高 | 低 | 这是 prompt 工程，不是规则引擎。利用认知顺序引导 LLM 注意力分配 |
| **修复项 2: Schema 铁律** | 🟢 高 | 低 | 确定性约束（字段名不能错）用代码校验是正确的 |
| **修复项 2: 硬性 Gate** | 🟢 高 | 低 | "非空检查"是确定性任务，用代码做是对的 |
| **修复项 3: Reviewer AI Coding 可用性** | 🟢 高 | 低 | 让 LLM 判断"AI Agent 拿到能不能开工"是理解力任务 |
| **修复项 4: Harness Gate 体系** | 🟢 高 | 低 | Code-Based 检查 + LLM-Based 评估分层，是正确的 AI Native 架构 |

## 关键发现

### 发现 1：Specifier 的三条规则是"规则引擎退化"的铁证

修复项 2 中的三条规则直接违反了 AI Native 原则：

**规则 1 — complexity 判定**（修复方案 §4.2）：
```
complex（满足任一）：
- 涉及 ≥3 个组件协调
- 在关键路径上且 dependencies ≥2
- 涉及外部商业协议/支付集成
```

**问题**：这是用数字阈值做分类。LLM 读一遍 WP 的 title + objective + dependencies，就能"感觉到"它是 complex 还是 simple。给 LLM 塞 if-then 规则，不如直接问它"这个任务有多复杂？为什么？"

**规则 2 — requirements 关键词匹配**（诊断报告修复 6）：
```
| WP | 匹配关键词 |
| WP-001 | CDN, DNS, SSL, DDoS, WAF, Bot, Cloudflare, ICP |
| WP-002 | 网关, 路由, 故障切换, OpenAI, 兼容, SSE, 计量 |
```

**问题**：这是 2020 年的关键词匹配 NLP。LLM 完全能理解"REQ-005: 支持 DeepSeek 供应商"和"WP-003: 供应商通道集成"之间的语义关联。用关键词匹配表是在把 LLM 降级成 grep。

**规则 3 — outputs 推导模板**（诊断报告修复 3）：
```
| 模块类型 | 预期 outputs 模板 |
| API 网关 (COMP-001) | src/gateway/, docker-compose.yml, config/routes.yaml |
```

**问题**：这是硬编码映射。如果项目结构变了、技术栈变了，这些模板就全错了。LLM 完全能根据技术栈（Go + Docker + PostgreSQL）推导出合理的文件结构。

### 发现 2：核心问题的诊断方向错了

诊断报告发现了"Specifier 填不满字段"的问题，但给出的修复方向是**"给 Specifier 更多规则来填"**。

这就像发现一个人填不好表格，然后给他一本 50 页的填表指南。问题可能不是指南不够厚，而是：
1. **表格本身设计有问题**（字段太多、粒度不对）
2. **填表人缺乏必要信息**（不是规则能解决的）
3. **填表人的注意力被其他东西劫持了**（诊断已经发现了 AC Rubric 劫持，但修复方案又加了更多规则）

### 发现 3：Harness Gate 是正确的 AI Native 分层

修复项 4（Harness 体系）是方案中**最 AI Native 的部分**：

- **Code-Based Gate**：确定性检查（非空、Schema 合规、无环）→ 用 Python 代码做 → 正确 ✅
- **LLM-Based Gate**：语义判断（"AI Agent 能直接开工吗？"）→ 让 LLM 理解后判断 → 正确 ✅
- **分层清晰**：快速确定性检查（<2s）+ 慢速语义评估（~30s）→ 符合"确定性任务用代码，语义任务用 LLM" ✅

**但有一个隐患**：Gate 3（Specifier Harness）的 code_based 检查项中包含了"requirements_non_empty"和"outputs_non_empty"。如果上游信息不足以填充这些字段，Gate 会 FAIL，然后反馈给 Specifier 重试——但 Specifier 重试时仍然没有足够信息，导致死循环。**这不是 Specifier 的问题，是信息流架构的问题。**

### 发现 4：AI Coding 消费者诊断已经指出了更深层的问题

消费者诊断报告的关键发现：

> **不是"Specifier 不够努力"，而是信息流架构决定了某些字段在 Specifier 阶段不可填。**

| 字段 | Specifier 能填吗 | 原因 |
|------|:---:|------|
| `context_files` | ❌ Greenfield 不能 | 代码不存在 |
| `outputs` (具体文件) | ❌ Greenfield 不能 | 目录结构未定义 |
| `budget.tokens` | ❌ 不能 | 依赖 context_files 和 model_tier |

**但 V3.1 修复方案的回应是**：给 Specifier 更多规则来填这些字段。这是在用规则穷举对抗信息缺失——不可能赢。

### 发现 5：方案触发了 AI Native 红线

| 红线 | 触发情况 |
|------|----------|
| **R6**: 禁止在确定性任务上用 LLM 做代码能做的事 | ✅ 未触发（Harness Gate 用代码做确定性检查） |
| **R7**: 禁止 bloated prompt | ❌ **触发** — Specifier prompt 已经很长，修复方案又增加了 complexity 判定表、关键词匹配表、outputs 推导模板、执行顺序指令、Schema 铁律、硬性 Gate... |
| **R1**: 禁止按岗位分角色调专家 | ✅ 未触发 |
| **R2**: 禁止在没有可自动化验证的 done 标准前执行 | ✅ 未触发（Harness Gate 提供了可自动化验证） |

## 替代方案

### 替代方案 1：让 LLM 理解，而不是给 LLM 规则

**当前做法**（规则引擎）：
```
complexity 判定规则：
- 涉及 ≥3 个组件协调 → complex
- 只涉及 1 个组件 → simple
- 其余 → medium
```

**AI Native 做法**（让 LLM 理解）：
```
对每个 WP，判断其 complexity（simple/medium/complex）。
判断依据：
- 技术复杂度（涉及多少种技术栈？有无分布式事务？）
- 协调复杂度（需要多少组件配合？有无跨服务调用？）
- 领域复杂度（有无支付/合规/安全要求？）
给出判断和一句话理由。
```

**区别**：前者是 if-else 分类器，后者是让 LLM 发挥理解力。LLM 完全能"读懂"一个 WP 的复杂度，不需要你告诉它"≥3 个组件 = complex"。

### 替代方案 2：用语义匹配替代关键词匹配

**当前做法**（规则引擎）：
```
requirements 关联规则：
| WP | 匹配关键词 |
| WP-001 | CDN, DNS, SSL, DDoS, WAF |
```

**AI Native 做法**（让 LLM 理解）：
```
对每条 REQ，判断它与每个 WP 的语义关联度。
关联度 = 高/中/低/无关。
只将"高关联"的 REQ 写入 WP 的 requirements 字段。
给出一句话说明为什么关联。
```

**区别**：关键词匹配无法处理同义词、隐含关联、跨领域需求。LLM 的语义理解可以。

### 替代方案 3：接受"有些字段 Specifier 填不了"的现实

**当前做法**：给 Specifier 塞规则，逼它填（ outputs 推导模板、[ESTIMATED] 标注）。

**AI Native 做法**：
1. 在 Schema 中区分 `specifier_filled` 和 `agent_filled` 字段
2. Specifier 只填它**能填**的字段（objective, AC, complexity, requirements）
3. Agent 执行时自己填 `context_files`, `outputs`, `acceptance_tests`
4. Harness Gate 只检查 Specifier 该填的字段，不检查 Agent 该填的字段

**区别**：前者是在对抗信息缺失（用规则弥补），后者是顺应信息流架构（让对的角色填对的字段）。

### 替代方案 4：减少 Specifier 的规则负担，而不是增加

**当前方向**：Specifier prompt 已经有 70% 的 AC Rubric + 15% 元数据指导 + 15% 格式指导。修复方案又增加了：
- complexity 判定表（+5%）
- requirements 关键词匹配表（+5%）
- outputs 推导模板（+5%）
- 执行顺序指令（+3%）
- Schema 铁律（+3%）
- 硬性 Gate（+3%）

**总计**：Specifier prompt 将增加 ~25% 的内容，达到约 120% 的原始体量。这正是 R7（bloated prompt）的典型案例。

**AI Native 方向**：**减少** Specifier 的规则负担，让它专注于理解：
1. 删除 complexity 判定表 → 让 LLM 自己判断
2. 删除 requirements 关键词匹配 → 让 LLM 自己匹配
3. 删除 outputs 推导模板 → 改为 Architect 在蓝图中直接给出（上游负责）
4. 保留 Schema 铁律和硬性 Gate → 这是确定性约束，用代码校验

## 核心问题的回答

> 如果一个修复方案给 Specifier 增加了 20 条规则，但它仍然填不满字段，那问题到底出在哪？是规则不够多，还是方法论错了？

**答案：方法论错了。**

问题不在"规则不够多"，而在三个更深层的原因：

1. **信息流架构问题**：某些字段在 Specifier 阶段根本填不了（Greenfield 没有文件可引用）。给再多规则也填不出不存在的信息。

2. **角色职责错位**：Specifier 被要求同时做 6 件事（AC 创作 + 元数据填充 + 复杂度估算 + 需求关联 + 文件推导 + 风险传递）。这超出了单个 prompt 的认知带宽。修复方案说"先填表后创作"，但没有减少任务数量。

3. **规则引擎退化**：用 if-then 规则替代 LLM 理解力。每增加一条规则，LLM 的理解力就被压制一分。最终 LLM 变成了一个规则执行器，而不是一个理解者。

**正确的修复方向**：
- 不是"给 Specifier 更多规则"，而是"让 Specifier 更少规则、更多理解"
- 不是"逼 Specifier 填所有字段"，而是"让对的 Agent 填对的字段"
- 不是"用关键词匹配"，而是"用 LLM 语义理解"
- 不是"增加 prompt 体量"，而是"减少 prompt 体量 + 增加 Harness 代码检查"

## 总结

| 维度 | 评分 | 说明 |
|------|:---:|------|
| **Harness Gate 体系** | 🟢 优秀 | Code-Based + LLM-Based 分层，是正确的 AI Native 架构 |
| **Architect 增强** | 🟢 良好 | 让 LLM 输出实现蓝图是发挥理解力 |
| **Specifier complexity 规则** | 🔴 退化 | if-then 数字阈值，LLM 能直接理解 |
| **Specifier requirements 关键词匹配** | 🔴 严重退化 | 2020 年 NLP 做法，违反 AI Native 核心原则 |
| **Specifier outputs 推导模板** | 🟡 中性 | 需要一些锚点，但不应该是硬编码映射表 |
| **整体 AI Native 浓度** | 🟡 ~55% | Harness 和 Architect 拉高了分数，Specifier 的三条规则严重拉低 |

**一句话总结**：V3.1 修复方案在"验证层"（Harness）是 AI Native 的，但在"生成层"（Specifier）退化为规则引擎。修复方向应该是**减少 Specifier 的规则负担、让 LLM 发挥理解力**，而不是**增加更多 if-then 规则**。
