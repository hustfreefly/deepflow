# 用户体验评审

## 用户等待心理分析

30-60 分钟的等待属于**长时间异步任务**，用户心理模型可拆解为三个阶段：

| 阶段 | 时间窗口 | 用户心理 | 信息需求 |
|------|---------|---------|---------|
| **启动确认** | 0-2 分钟 | "真的开始了吗？" | 必须：启动确认 + 预计耗时 |
| **等待焦虑** | 2-30 分钟 | "还在跑吗？卡了吗？" | 需要：阶段性进度信号 |
| **预期收尾** | 30-60 分钟 | "快好了吧？" | 需要：最终结果 + 质量概要 |

**核心结论**：30-60 分钟不做任何进度推送，用户大概率会在 10-15 分钟后主动来问"还在跑吗？"——这比任何技术方案都更真实地反映了信息需求。

但关键在于**用户要的不是"进度条"，而是"还在活着"的信号**。一条简单的"第 3/10 阶段完成"足以消除焦虑。

## 方案对比

| 方案 | 用户体验 | 实现复杂度 | 可靠性 | 推荐度 |
|------|---------|-----------|--------|--------|
| **A: cron 轮询（每 2 分钟）** | 每 2 分钟一条进度，过度打扰 | 中（需 cron + 状态文件 + 清理） | 高 | ⭐⭐ |
| **B: 用户主动问** | 最差。用户需要记住来问，问了才答 | 低 | 高 | ⭐ |
| **C: 只通知完成/失败** | 简洁。中间无干扰，只在关键节点推送 | 最低（已有 announce 机制） | 高 | ⭐⭐⭐⭐ |
| **D: 主 Agent 不 yield，自己轮询** | 理论上最实时，但主 Agent 被阻塞，可能导致 session 超时/卡顿 | 高 | 低 | ⭐ |

### 方案 A 深度分析：cron 每 2 分钟
- **好消息**：用户体验好，感知流畅
- **坏消息**：30 分钟 = 15 条消息。15 条"阶段 2 完成""阶段 3 完成"对用户的边际价值递减极快。第 1 条有用，第 5 条变噪音，第 10 条被忽略
- **额外成本**：cron 需要管理生命周期（启动/停止/清理），否则会有幽灵 cron 残留

### 方案 D 深度分析：主 Agent 不 yield
- **致命问题**：主 Agent 被占用期间，无法响应用户其他请求
- **风险**：如果用户在这期间发了新消息，主 Agent 不响应，体验比没进度更差
- **架构反模式**：主 Agent 不应该做长轮询

## 推荐方案

### 首选：方案 C（完成/失败通知）+ 轻量增强

**核心理由**：
1. **已有机制**：sub-agent announce 天然支持完成时回传，零额外实现
2. **失败也能到**：sub-agent 失败时同样会回传，用户能第一时间知道
3. **不阻塞主 Agent**：yield 后主 Agent 可正常响应其他请求
4. **30-60 分钟的合理预期**：如果用户提前知道需要等这么久，方案 C 是可接受的

**轻量增强（可选，实现成本极低）**：
在启动时给用户一条消息，包含：
- ✅ 任务已启动
- 📊 共 10 个阶段
- ⏱ 预计 30-60 分钟
- 💬 "期间我可以处理其他请求，完成后我会通知你"

这条消息的价值：**设定正确预期**，消除"启动确认"阶段的焦虑。

### 如果用户强烈要求进度推送：方案 A'（改进版 cron）

如果评审后用户反馈"20 分钟后忍不住来问"是高频事件，升级到 A'：

- **频率改为 5 分钟一次**（而非 2 分钟），30 分钟最多 6 条，噪音可控
- **只推关键里程碑**（阶段 3/6/9 完成），而非每个阶段
- **cron 在子任务完成时自动注销**，不留幽灵进程
- **消息格式极简**：`📊 DeepFlow 进度：6/10 阶段完成，预计剩余 15 分钟`

## 用户故事

### 理想用户体验流程

```
用户: "帮我设计一个用户登录系统的方案"

主 Agent: "✅ 已启动 DeepFlow Solution Pro 管线
          📊 共 10 个阶段，预计 30-60 分钟
          💬 期间你可以继续问我其他问题，完成后我会通知你"

[主 Agent yield，等待子任务完成]
[用户在此期间可以问其他问题，主 Agent 正常响应]

[35 分钟后，子任务完成，回传 announce]

主 Agent: "✅ 方案设计完成！用时 35 分钟
          
          快速摘要：
          1. 架构：JWT + OAuth 2.0 双认证
          2. 数据库：PostgreSQL + Redis session
          3. 安全：BCrypt + Rate Limiting + CSRF
          
          完整方案已保存至 [路径]
          需要我解释某个部分，还是直接开始实施？"
```

### 失败场景

```
[15 分钟后，子任务因 API 限流失败]

主 Agent: "⚠️ 方案设计在第 4 阶段失败
          
          原因：外部 API 触发了限流（429 Too Many Requests）
          影响：第 1-3 阶段结果已保存，第 4-10 阶段未执行
          
          选项：
          1. 5 分钟后重试（自动退避）
          2. 跳过第 4 阶段，继续后续阶段
          3. 手动提供第 4 阶段所需信息
          
          你想怎么处理？"
```

**失败通知的关键**：不是告诉用户"失败了"，而是告诉用户"前 X 阶段成果还在 + 有 2-3 个恢复选项"。
