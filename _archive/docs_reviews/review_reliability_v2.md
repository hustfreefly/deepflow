## V2 新发现的问题

### P2（建议改进，不阻塞实施）

| # | 严重度 | 问题 | 说明 | 建议 |
|---|--------|------|------|------|
| N1 | P2 | `compact-history` 可能丢失关键失败细节 | 压缩为摘要后，Orchestrator 可能忘记之前犯过的错误，重复同样的失败路径。 | compact-history 保留最近 2 个阶段的完整失败记录，只压缩更早的阶段。或在摘要中强制包含"失败历史"字段。 |
| N2 | P2 | 并行阶段部分失败时策略模糊 | "等待其他完成后统一处理"不够具体。如果 A 成功 B 失败，重做 B 时 A 的输出是否保留？B 重试耗尽是否阻塞管线？ | 在 prompt 的错误恢复策略菜单中增加并行失败的具体条目。建议：已完成并行阶段的结果保留，只重做失败阶段；失败阶段重试耗尽时，如果该阶段 `required: true` 则阻塞，否则标记 skipped 继续。 |
| N3 | P2 | `write-status` 时序窗口 | 状态文件由 LLM 主动调用 write-status 更新。如果 Orchestrator 在 Worker 完成后、write-status 调用前崩溃，状态文件不反映最新进度。 | 可接受的风险——resume-context 会检查 .heartbeat 和实际输出文件，不完全依赖 pipeline_state.json。建议在 resume-context 中增加"文件扫描"逻辑：如果 blackboard 目录有输出但状态文件未更新，自动修正状态。 |
| N4 | P2 | Judge Worker 的评估可靠性 | 独立 Judge Worker 是好的设计（避免自评），但 Judge 本身也是 LLM，可能给出不一致的评估。 | 建议 Judge 评估结果与 Python gate 结果交叉验证：如果 Judge pass 但 validate-quality fail，以 quality 为准。 |

### 观察（非问题，供参考）

- **`check-retry-limit` 的 `--max` 参数来源**：方案中 `check-retry-limit <stage> --max <N>` 的 N 来自 Orchestrator 传入。如果 Orchestrator 传入一个很大的 N 就绕过了限制。建议 `--max` 从 `stage-dependencies.json` 的 `max_retries` 字段读取，不接受命令行覆盖（或只允许缩小不允许放大）。
- **`.heartbeat` 写入频率**：方案说"每完成一个阶段写入"，但如果一个阶段内部有多个子步骤，粒度可能不够。可以考虑每调用一次 io_helper 命令就更新 .heartbeat 的时间戳。

## 可靠性架构评估（V2 整体）

```
┌─────────────────────────────────────────────────────────┐
│  第一层：Session 超时（硬限制）                           │
│  Worker: 300s | Orchestrator: 1800s | 不可绕过           │
├─────────────────────────────────────────────────────────┤
│  第二层：预算检查（代码护栏）                              │
│  check-budget: 总时间/token 上限                          │
│  check-retry-limit: 单阶段重试上限                        │
│  → 超限时强制上报主 Agent                                 │
├─────────────────────────────────────────────────────────┤
│  第三层：状态安全（确定性保障）                            │
│  枚举校验 + 原子写入 + .heartbeat 心跳                    │
│  → 状态文件不会损坏，崩溃后可恢复                          │
├─────────────────────────────────────────────────────────┤
│  第四层：断点恢复（resume-context）                       │
│  启动时自动检查 → 从断点继续 → 不重做已完成阶段            │
├─────────────────────────────────────────────────────────┤
│  第五层：回滚兜底（SOP + 版本标记）                       │
│  pipeline_state.json 版本标记 → V4 resume 模式兼容        │
└─────────────────────────────────────────────────────────┘
```

**评价**：这是一个分层的可靠性架构，从硬限制（session 超时）到软限制（预算检查）到恢复（断点续接）到兜底（回滚），层次清晰、互为补充。与 V1 的"可靠性裸奔"相比是质的飞跃。
