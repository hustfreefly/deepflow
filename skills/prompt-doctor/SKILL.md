# Prompt Doctor Skill V2.1

> **定位**：Prompt 设计时的"结构检查器 + 改进建议器"——确保 Prompt 结构完整、流程可执行、稳健性优先
> **核心原则**：稳健性优先（Recover Smart，不是 Fail Fast）+ 契约笼子
> **分析时机**：Prompt 编写时 / 修改后 / 崩溃后根因分析

---

## 0. 契约笼子设计模式（V2.1 新增 — 来自 Solution Pro 实战）

### 0.1 什么是契约笼子？

**契约笼子 = 输入契约 + 输出契约 + 错误处理契约**

```markdown
## 🔴 契约笼子（稳健性优先）

### 输入契约（必须满足）
- ✅ 主输入必须存在且非空
- ✅ 文件大小必须 >= 最小阈值
- ✅ 文件内容必须是有效 JSON
- ❌ 如果不满足 → 触发智能恢复（不是直接失败）

### 输出契约（必须满足）
- ✅ 输出必须通过 Schema 校验
- ✅ 必须包含所有必需字段
- ❌ 如果不满足 → 报告详细失败原因

### 错误处理契约（智能恢复，不降级）
| 错误类型 | 恢复策略 |
|---------|----------|
| 瞬时故障 | 等待后重试（最多 N 次）|
| 可恢复错误 | 修复后重试 |
| 不可恢复错误 | 报告详细失败原因（已尝试什么、建议什么）|
```

### 0.2 上级设定机制（Worker 执行契约由 Module Agent 注入）

**架构决策**：Worker 的执行契约由 Module Agent 在 spawn task 中统一注入，而不是每个 Worker prompt 自己写。

**为什么？**
- 单一信息源：Module Agent 是编排者，它决定每个 Worker 的行为规范
- 减少重复：15 个 Worker 不需要各自维护同样的契约
- 更容易维护：改一个 Module Agent 就能影响所有它管理的 Workers
- 符合架构原则：编排层负责编排逻辑，执行层专注执行

**实现方式**：
```python
# Module Agent spawn Worker 时注入执行契约
sessions_spawn(
    task=f"""cd {_deepflow_root} && PYTHONPATH=.
你执行的所有 Python 命令必须以 cd {_deepflow_root} && PYTHONPATH=. 开头。

## 🔴 你的执行契约（Module Agent 注入）
- **任务边界**：你只负责 {worker_role}。你不负责重试、错误恢复、降级输出。
- **完成条件**：输出写入 blackboard 且通过 Schema 校验。
- **错误报告**：如果无法完成，写入 stages/.worker_failed.json，包含 {{"error_type": "unrecoverable", "error_message": "具体错误", "attempted_actions": ["已尝试的动作"]}}。
- **禁止行为**：不要自行重试，不要降级输出，不要跳过步骤。

## 你的完整指令
用 read 工具读取: {_prompt_path}

读取后按指令执行。"""
)
```

**Worker prompt 只保留**：角色 + 输入 + 输出格式 + 执行步骤。

### 0.3 分层检查策略（来自实战）

**检查优先级**：
- **Layer 1 + Layer 3**：必须通过（流程可执行性 + 上下文契约）
- **Layer 2**：推荐通过（过程质量）

**为什么 Layer 2 是推荐？**
- Layer 2（质量预期、验证标准、示例）是"锦上添花"
- Layer 1 + Layer 3 是"流程能跑通"的必要条件
- 实战中，Layer 1 + Layer 3 通过后，系统就能稳定运行
- Layer 2 可以在后续迭代中逐步补充

## 1. 概述

Prompt Doctor 是一个轻量级（< 5min）的 Prompt 诊断工具，用于确保 Agent Prompt 满足"流程可执行性"、"上下文契约"和"过程质量"三个维度的要求。

### 1.1 核心原则：稳健性优先

**❌ V1 错误方向（Fail Fast）**：
- Worker 遇到问题 → 报错退出
- Module Agent 重试 1 次 → 失败就放弃
- 结果：本来可以恢复的问题变成了系统失败

**✅ V2 正确方向（Recover Smart）**：
- Worker 遇到问题 → 尝试恢复（重试、降级、报告问题但继续）
- Module Agent 有上限的重试（比如 3 次）→ 重试失败后尝试降级方案
- 结果：系统尽可能完成任务，只有"无法恢复"才报告失败

### 1.2 与现有 Skill 的边界

| Skill | 时机 | 对象 | 核心问题 |
|-------|------|------|---------|
| **Prompt Doctor**（本 Skill） | Prompt 编写时 | 单个/多个 Prompt 文本 | "这个 Prompt **写对**了吗？" |
| **AgentDryRun** | 上线前/修改后 | Prompt + Schema + 代码 | "这个系统**能跑通**吗？" |
| **Doctor** | 运行中/失败后 | 实际执行轨迹 | "这次运行**为什么失败**？" |

## 2. AI Native 设计原则

### 2.1 能力正交：谁做什么？

| 层 | 职责 | 工具 |
|----|------|------|
| **代码层** | 格式验证、状态机控制、重试计数、超时检测 | Pydantic、状态机、计数器 |
| **LLM 层** | 语义理解、质量判断、失败原因分析 | LLM-as-Judge |
| **Prompt 层** | 任务边界、完成语义、质量预期、恢复策略 | Prompt 指令 |

### 2.2 Prompt 是契约，不是指令

**❌ 反模式**：
```
你是 XXX Agent。
你必须做 A、B、C。
如果失败，重试。
```

**✅ 正确模式**：
```
## 角色与边界
你是 Solution Pro Orchestrator，负责从 Living Spec 生成 Acceptance Criteria。
你不负责修改 Living Spec，也不负责执行测试。

## 推进策略
| 当前状态 | 触发条件 | 下一状态 | 恢复策略 |
|---------|---------|---------|---------|
| 初始化 | 读取 Living Spec 成功 | Phase 1 | → 等待 30s 后重试 |
| Phase 1 | 质量达标 | Phase 2 | → 降级处理（跳过非关键检查）|

## 完成条件
- 成功：所有 AC 写入 artifacts/acceptance_criteria.md
- 无法恢复：Phase 1 重试 3 次仍失败 → 输出详细失败报告（包含已尝试什么、建议什么）

## 数据流契约
- 输入：artifacts/living_spec.md
- 中间产物：artifacts/phase1_output.json
- 输出：artifacts/acceptance_criteria.md
```

## 3. Prompt 设计三层架构

```
┌─────────────────────────────────────────┐
│  Layer 3: 上下文契约（Context Contract）  │
│  - 每步的输入源、输出目标、中间产物位置    │
│  - Agent 知道"从哪里读数据、往哪里写结果"  │
├─────────────────────────────────────────┤
│  Layer 2: 过程质量（Process Quality）     │
│  - 质量预期、验证标准、示例                │
│  - Agent 知道"什么是好的输出"              │
├─────────────────────────────────────────┤
│  Layer 1: 流程可执行性（Flow Executability）│
│  - 任务边界、推进策略、完成条件、恢复机制  │
│  - Agent 知道"如何一步步达成目标"          │
│  - 前置条件，不通则后续为零               │
└─────────────────────────────────────────┘
```

**优先级**：Layer 1 > Layer 3 > Layer 2

## 4. Layer 1：流程可执行性（必须）

### 4.1 六要素（稳健性优先版）

| 要素 | 说明 | 检查标准 |
|------|------|----------|
| **任务边界** | 你负责什么、不负责什么 | Prompt 中有明确的"负责/不负责"声明 |
| **推进策略** | 如何一步步达成目标 | 有显式的状态转移表或流程图 |
| **完成条件** | 什么情况下算完成、什么情况下算失败 | 有"成功条件"和"无法恢复条件"的显式声明 |
| **恢复机制** | 遇到问题时如何恢复 | 有重试策略、降级策略、替代方案 |
| **错误分类** | 不同类型的错误如何处理 | 区分瞬时故障/可恢复错误/不可恢复错误 |
| **中间产物持久化** | 每步完成后，结果写到哪里？ | 有明确的文件路径或 blackboard 位置 |

### 4.2 状态转移表模板（稳健性优先）

```markdown
## 状态流转

| 当前状态 | 触发条件 | 下一状态 | 恢复策略 |
|---------|---------|---------|---------|
| 初始化 | 读取 Living Spec 成功 | Phase 1 | → 等待 30s 后重试（最多 3 次）|
| Phase 1 | 质量达标 | Phase 2 | → 降级处理（跳过非关键检查）|
| Phase 2 | 所有 AC 写入文件 | 完成 | → 输出详细失败报告 |
```

### 4.3 错误分类与恢复策略

| 错误类型 | 特征 | 恢复策略 | 示例 |
|---------|------|---------|------|
| **瞬时故障** | 网络超时、临时不可用 | 自动重试（指数退避）| 文件读取超时 |
| **可恢复错误** | 输入格式错误、部分数据缺失 | 尝试修复 + 重试 | JSON 格式错误 → 尝试修复 |
| **不可恢复错误** | 关键输入缺失、核心功能失败 | 报告详细失败原因 | 关键文件不存在 |

### 4.4 反模式清单（V1 遗留问题）

| 反模式 | 症状 | 修复 |
|--------|------|------|
| **Fail Fast 思维** | "遇到问题就退出" | 改为"尝试恢复，无法恢复时才报告" |
| **硬编码重试次数** | "重试 3 次就放弃" | 改为"根据错误类型决定恢复策略" |
| **无降级方案** | "关键步骤失败就整体失败" | 改为"尝试降级处理（跳过非关键步骤）" |
| **错误信息丢失** | "只说失败，不说原因" | 改为"输出详细失败报告（已尝试什么、建议什么）" |

## 5. Layer 3：上下文契约（必须）

### 5.1 三要素

| 要素 | 说明 | 检查标准 |
|------|------|----------|
| **输入源** | 从哪里读取数据 | 有明确的文件路径或变量名 |
| **输出目标** | 结果写到哪里 | 有明确的文件路径或 blackboard 位置 |
| **中间产物** | 每步的产物是什么 | 有产物清单 + 存放位置 |

### 5.2 示例

```markdown
## 数据流契约

### 输入
- Living Spec: `artifacts/living_spec.md`
- 质量报告: `artifacts/quality_report.json`

### 输出
- Acceptance Criteria: `artifacts/acceptance_criteria.md`
- 执行报告: `artifacts/execution_report.json`（包含失败原因和建议）

### 中间产物
- Phase 1 输出: `artifacts/phase1_output.json`
- Phase 2 输出: `artifacts/phase2_output.json`
```

## 6. Layer 2：过程质量（推荐）

### 6.1 三要素

| 要素 | 说明 | 检查标准 |
|------|------|----------|
| **质量预期** | 输出应该达到什么标准 | 有量化指标或 golden example |
| **验证标准** | 如何判断输出是否合格 | 有检查清单或验证代码 |
| **示例** | 好的输出长什么样 | 至少有 1 个正面示例 + 1 个负面示例 |

### 6.2 验证分层

| 验证类型 | 放置层 | 职责 |
|----------|--------|------|
| **格式/结构验证** | Pydantic 代码层 | 字段存在性、类型、无循环依赖 |
| **语义/质量验证** | LLM-as-Judge 层 | 输出是否符合质量预期 |
| **流程合规验证** | Prompt 指令层 | 完成条件、恢复策略是否被遵守 |

## 7. Prompt vs Code 归属原则

| 内容 | 归属 | 原则 |
|------|------|------|
| 状态转移逻辑 | **代码层**（状态机） | 控制流必须确定性 |
| 重试计数 | **代码层** | 确定性计数 |
| 完成语义判断 | **Prompt 层** | 需要理解"质量达标"的含义 |
| 恢复策略选择 | **Prompt 层** | 需要理解错误类型和上下文 |
| 失败原因输出 | **Prompt 层** | 语义生成 |
| 任务边界 | **Prompt 层** | LLM 需要理解"不做什么" |
| 质量验证标准 | **混合**：Prompt 声明 + 代码强制 | 分层验证 |

**核心原则**：控制流归代码，语义判断归 Prompt，两者通过 blackboard 文件交互。

## 8. Prompt Doctor 检查清单（V2.1 稳健性优先版）

### 8.1 Layer 1 检查（必须通过）

- [ ] 有明确的"任务边界"声明（负责/不负责）
- [ ] 有显式的"状态转移表"（每个状态有出边）
- [ ] 有"完成条件"声明（成功条件 + 无法恢复条件）
- [ ] 有"恢复机制"定义（重试策略、降级策略、替代方案）
- [ ] 有"错误分类"定义（瞬时故障/可恢复错误/不可恢复错误）
- [ ] 有"中间产物持久化"定义（文件路径或 blackboard 位置）
- [ ] **❌ 没有 Fail Fast 思维**（不是"遇到问题就退出"）
- [ ] **✅ 有契约笼子**（输入契约 + 输出契约 + 错误处理契约）

### 8.2 Layer 3 检查（必须通过）

- [ ] 有明确的"输入源"定义（文件路径或变量名）
- [ ] 有明确的"输出目标"定义（文件路径或 blackboard 位置）
- [ ] 有"中间产物"清单（产物名 + 存放位置）

### 8.3 Layer 2 检查（推荐通过）

- [ ] 有"质量预期"定义（量化指标或 golden example）
- [ ] 有"验证标准"定义（检查清单或验证代码）
- [ ] 有正面示例 + 负面示例

### 8.4 通用检查

- [ ] Prompt 结构清晰（分层 + 编号，不超过 3000 token）
- [ ] 关键约束放在顶部（前 500 token）
- [ ] 有负面示例（"以下行为违反约束"）
- [ ] spawn task 使用文件引用（不是内联 prompt）
- [ ] **Worker 执行契约由 Module Agent 注入**（不是每个 Worker 自己写）

## 9. 使用方法

### 9.1 输入

- Prompt 文本（必须）
- Agent 执行日志（可选，用于诊断"为什么流程跑不通"）

### 9.2 输出

- 结构化诊断报告（Markdown）
- 包含：
  - 问题分类（Layer 1 / Layer 3 / Layer 2）
  - 严重度（P0 / P1 / P2）
  - 修复建议（以稳健性优先为原则）
  - 修复后的 prompt 片段（可选）

### 9.3 执行流程

1. 读取 Prompt 文本
2. 按检查清单逐项检查
3. 生成诊断报告
4. 给出修复建议（确保符合"稳健性优先"原则）

## 10. 反模式总结

### 10.1 Prompt 设计反模式

1. **Fail Fast 思维**：遇到问题就退出 → 降低系统稳健性
2. **硬编码重试次数**：重试 3 次就放弃 → 没有根据错误类型决定恢复策略
3. **无降级方案**：关键步骤失败就整体失败 → 没有尝试跳过非关键步骤
4. **错误信息丢失**：只说失败，不说原因 → 上游无法决策
5. **状态靠推理**：不显式写出状态机 → Agent 自己猜，猜错就崩
6. **每个 Worker 自己写契约**：15 个 Worker 各自维护同样的契约 → 维护成本高、容易不一致
7. **Worker 自行重试**：Worker 遇到问题自己重试 → 与 Module Agent 的重试逻辑冲突

### 10.2 架构反模式

1. **完成条件只放 Prompt**：Prompt 是建议性，代码才是强制性
2. **重试/超时放 Prompt**：LLM 无时间感知，计数可能出错
3. **控制流归 Prompt**：控制流必须确定性，归代码层
4. **双入口函数共存**：统一入口 + 物理废弃旧入口
5. **Worker 执行契约分散**：每个 Worker prompt 自己写契约 → 应该由 Module Agent 统一注入
6. **无契约笼子**：只有输入/输出定义，没有错误处理契约 → 无法稳健恢复
