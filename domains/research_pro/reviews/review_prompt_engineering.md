## 一、总体评价

### **评级：良好（B+）**

改进计划整体方向正确，问题诊断精准（5 条根因与 7 维差距表对齐），从"通才概述"到"专家白皮书"的目标清晰。Prompt 设计展现了较强的工程化思维：JSON 输出约束、类型路由、置信度分级、闭环评审都是高价值改进。

### 2.1 planning.md — 研究类型识别设计

**评分：3/5**

#### 优点
1. **问题抓得准**：当前 planning.md 对所有研究类型使用相同框架，是报告质量低的核心根因之一。新增 `research_type` 字段 + 模板路由是正确方向。
2. **JSON 结构化输出**：planning.md 已有严格的 JSON 输出格式，新增 `research_type` 字段与现有架构无缝衔接。
3. **5 类划分覆盖合理**：`tech_process | investment | market_research | competitive_analysis | general` 涵盖了 Research Pro 的主要使用场景。

#### 问题

**P0 — 类型判断规则设计缺陷**

改进计划中的类型判断规则采用关键词硬匹配：
```
包含"工艺/封装/制程/良率/失效/材料" → tech_process
包含"股票/投资/估值/财报/PE/PB" → investment
```

**问题 1：关键词冲突/歧义未处理**
- "AI 芯片市场规模" → 同时匹配 `tech_process`（芯片）和 `market_research`（市场规模）
- "半导体投资分析" → 同时匹配 `tech_process`（半导体）和 `investment`（投资）
- "封装材料供应商市场份额" → 同时匹配 `tech_process` 和 `market_research`

计划中未定义优先级或冲突解决机制。实际使用中，跨领域研究（技术+市场、技术+投资）非常常见。

**问题 2：未利用 LLM 语义理解能力**
关键词匹配是规则引擎的工作方式，不是 LLM 的工作方式。既然 planning 阶段本身由 LLM 执行，应该利用 LLM 的语义理解能力做分类，而非硬编码关键词列表。关键词列表可以作为 hint/few-shot examples，但不应作为唯一判断依据。

**问题 3：边界条件未定义**
- 输入"特斯拉"→ 投资分析？技术工艺？竞品对比？取决于用户意图，但规则无法区分
- 输入"台积电"→ 同上
- 输入"CoWoS"→ 可能是技术工艺，也可能是市场研究

**问题 4：缺少复合类型支持**
现实中很多研究是跨类型的：
- "CoWoS-L 封装工艺的投资价值" = tech_process + investment
- "AI 芯片竞争格局的技术对比" = market_research + competitive_analysis + tech_process

当前设计只有单一类型，无法处理复合需求。

#### 改进建议

**建议 1：改用 LLM 语义分类 + 置信度**

```markdown
## 研究类型识别

根据用户查询的语义，判断研究类型。输出 `research_type` 和 `confidence`。

判断依据（优先级从高到低）：
1. 用户明确指定的分析角度（"从投资角度分析..."）→ 最高优先级
2. 核心实体的主要属性（"CoWoS-L封装工艺" → 技术工艺是核心属性）
3. 查询的动词/目标（"分析市场规模" → market_research）
4. 上下文暗示（"替代方案" → competitive_analysis）

对于跨领域研究，使用复合类型：
- "research_type": "tech_process+investment"
- 主类型在前，分析框架以主类型为主，辅类型维度作为附加章节

置信度规则：
- confidence >= 0.8: 直接执行
- 0.5 <= confidence < 0.8: 在确认步骤中向用户说明判断依据，请求确认
- confidence < 0.5: 列出候选类型，请用户选择
```

**建议 2：增加 few-shot 示例**

在 planning.md 中提供 5-8 个典型分类示例（含边界案例），比关键词列表更能引导 LLM 行为。

**建议 3：增加"研究角度"字段**

```json
{
  "research_type": "tech_process",
  "research_angle": "以工艺可靠性为核心视角，兼顾供应链分析",
  "secondary_types": ["market_research"],
  "type_confidence": 0.85
}
```

`research_angle` 让 LLM 不仅分类，还解释分类理由，便于用户确认和后续调试。

### 2.2 tech_analysis.md — 9 维度框架（计划中的设计）

**评分：4/5**

#### 优点
1. **维度覆盖全面**：从架构演进→工艺流程→材料→设备→良率→失效→改善→供应链→前瞻，形成了完整的技术分析链条。比 finance_analysis.md 的 10 维度在技术领域更专业。
2. **每个维度有具体的输出要求**：不只是维度名称，还有"需要输出什么"的描述（如"良率损失瀑布图"、"失效模式图谱"），降低了 LLM 的执行歧义。
3. **强调量化和机理**：多次要求"物理机理描述"、"量化数据"，直击当前报告"概述级"的痛点。
4. **9 维度逻辑递进**：从"是什么"（架构、工艺）→"为什么出问题"（良率、失效）→"怎么解决"（改善）→"谁在做"（供应链）→"未来怎样"（前瞻），符合工程思维。

#### 问题

**P1 — 认知负荷过高，可能导致"维度填充"**

9 个维度同时出现在 prompt 中，LLM 需要为每个维度生成内容。这会导致两个风险：

**风险 1：广度 vs 深度的权衡失衡**
LLM 的输出 token 有限（通常 8K-32K），9 个维度平均分，每个维度只能分到 ~1K tokens。结果可能是每个维度都"点到为止"，看似覆盖全面，实则每个维度都是概述级。

**反面案例**：当前 finance_analysis.md 有 10 个维度，实际执行中已经出现了"每个维度 2-3 段话"的填充问题。增加到 9 个维度（技术类）并不会改善这个问题。

**风险 2：维度间内容重复**
- "维度 3 材料体系" 和 "维度 4 设备生态" 与 "维度 8 供应链生态" 存在重叠
- "维度 6 失效模式" 和 "维度 7 改善方法论" 存在因果关联，分开写可能导致重复描述
- "维度 5 良率分析" 的量化数据与 "维度 6 失效模式" 的检测数据可能重复引用

**P2 — 部分维度的 LLM 可执行性存疑**

**维度 5 良率分析**：
> "良率损失瀑布图（每个环节的量化损失）"

问题：良率数据是半导体行业最敏感的商业机密，公开来源几乎不可能获得 TSMC CoWoS-L 的具体良率数字。LLM 可能会编造数据来"满足"prompt 要求。

**建议**：改为"良率趋势分析（基于公开信息的定性/半定量分析）"，并明确标注"数据不足时，给出行业估算范围而非精确数字"。

**维度 2 工艺流程**：
> "工艺窗口（温度/压力/时间的容许范围）"

问题：具体工艺窗口参数同样是高度机密。LLM 可能从学术论文中引用"典型值"，但用户可能误以为是实际产线参数。

**建议**：增加免责声明模板："以下工艺参数基于公开文献的典型值范围，实际产线参数可能因设备配置和产品规格而异。"

**P3 — 缺少"分析深度"分级**

9 个维度对所有研究主题一视同仁，但不同主题的深度需求不同：
- "CoWoS-L 封装工艺深度研究" → 全部 9 维度都需要深度分析
- "先进封装技术概览" → 可能只需要 5-6 个维度的中等深度分析
- "封装材料对比" → 维度 3（材料）需要深度，其他维度可以浅出

当前设计没有"深度分级"机制，可能导致简单主题被过度分析（浪费 token），复杂主题被均匀分析（深度不够）。

#### 改进建议

**建议 1：引入"核心维度 + 可选维度"分层**

```markdown
## 维度分层

### 核心维度（必须覆盖，深度分析）
- 维度 1: 架构演进
- 维度 2: 工艺流程
- 维度 6: 失效模式与根因

### 扩展维度（根据研究主题选择 3-4 个）
- 维度 3: 材料体系（材料相关主题必选）
- 维度 4: 设备生态（设备/产线相关主题必选）
- 维度 5: 良率分析（数据充足时选择）
- 维度 7: 改善方法论（与维度 6 联动）
- 维度 8: 供应链生态（市场/产业相关主题必选）
- 维度 9: 技术前瞻（所有主题推荐）

### 选择规则
由 Planning 阶段根据 research_angle 和 secondary_types 决定选择哪些扩展维度。
总维度数控制在 6-7 个，确保每个维度有足够深度。
```

**建议 2：增加"数据不足"处理指令**

在每个维度下增加：
```markdown
#### 数据不足处理
如果该维度的公开数据不足：
- 标注 "数据有限，以下为行业估算"
- 给出范围而非精确数字（如"良率估计在 85-92% 区间"）
- 引用最接近的公开来源并说明局限性
- 不要编造精确数据
```

**建议 3：增加维度间交叉引用规则**

```markdown
## 交叉引用规则
- 维度 6（失效模式）与维度 7（改善方法论）必须联动：每个失效模式必须对应至少一条改善方向
- 维度 3（材料）与维度 6（失效）联动：材料相关的失效模式必须引用维度 3 中的材料参数
- 维度 8（供应链）中的数据不要与维度 3/4 重复：维度 8 聚焦市场格局，不重复技术参数
```

### 2.3 quality_review.md — 工程质量评审（计划中的设计）

**评分：3/5**

#### 优点
1. **闭环设计正确**：报告生成后增加质量审查是必要的，"不通过则回退重写"的机制能有效提升输出质量。
2. **6 维度覆盖合理**：工程深度、量化程度、可操作性、引用质量、结构完整性、术语精确性 — 这 6 个维度确实是目前报告的主要薄弱环节。
3. **有明确的通过标准和回退机制**：24 分通过、18-23 局部回退、<18 整体重写，规则清晰。
4. **有防死循环设计**：`max_retries=2` 避免无限回退。

#### 问题

**P0 — 5 分制评分的 LLM 执行一致性问题**

**问题 1：评分标准的主观性**

以"工程深度"为例：
```
5分: 有物理/化学机理描述，引用学术论文
4分: 有技术细节描述，引用行业白皮书
3分: 有工艺参数，但缺乏机理分析
```

"有物理/化学机理描述"到什么程度算 5 分？一段话描述 Kirkendall 空洞形成机制 vs. 完整的数学模型推导，都算"有机理描述"，但深度天差地别。

LLM 评分的主要问题是 **评分者间一致性低**（同一个报告，不同次评分可能给出不同分数）。学术研究中，Cohen's Kappa > 0.6 才算可接受的一致性。5 分制下，LLM 的自身一致性通常在 ±1 分范围波动。

**问题 2：5 分制的区分度不足**

5 分制在实际使用中容易出现"趋中效应"：LLM 倾向于给 3-4 分，很少给 1 分或 5 分。6 个维度 × 3-4 分 = 18-24 分，恰好跨越"通过"和"回退"的边界线。这意味着：
- 一份"还行但不算好"的报告可能得 20 分 → 局部回退
- 经过回退后"稍微好一点"的报告可能得 22 分 → 还是局部回退
- 再回退一次得 23 分 → 还是局部回退 → 触发 max_retries → 强制通过

实际上，趋中效应可能导致"回退-回退-强制通过"的固定模式，而不是真正的质量驱动。

**问题 3：评分维度之间存在相关性**

"工程深度"和"术语精确性"高度相关（深度分析自然使用精确术语）。"量化程度"和"可操作性"也相关（量化数据支撑可操作建议）。6 个维度不是独立的，但评分标准假设它们独立。

这会导致：深度高的报告，术语分也高；量化高的报告，可操作性也高。6 个维度实际上可能只衡量了 3-4 个独立维度，总分的有效区分度更低。

**P1 — 评审 prompt 的执行者未明确**

计划中 `quality_reviewer.py` 是"评审执行模块"，但评审本身由谁执行？
- 如果用同一个 LLM（同一个模型）评审自己生成的报告，存在"自我评估偏差"
- 如果用不同的 LLM 或不同的 prompt 角色，需要明确配置

**P2 — 回退指令不够具体**

```json
"revision_instructions": "加强工程深度：补充失效模式的物理机理描述"
```

这个指令对人类可读，但对 LLM 执行来说不够具体。"补充物理机理描述" — 补充哪个失效模式的？补充到什么程度？从哪个来源获取数据？

#### 改进建议

**建议 1：改用"检查清单 + 二元评分"替代部分主观评分**

将"是否有 X"类型的标准改为二元检查（有/无），减少主观判断：

```markdown
### 工程深度检查清单（替代主观评分）

| # | 检查项 | 有(1)/无(0) |
|---|--------|------------|
| 1 | 是否引用了至少 2 篇学术论文或行业白皮书？ | |
| 2 | 是否有至少 1 个失效模式的物理/化学机理描述（>100字）？ | |
| 3 | 是否有工艺参数的具体数值范围（非定性描述）？ | |
| 4 | 是否有至少 1 个因果链分析（A→B→C 形式）？ | |
| 5 | 是否有数据来源的置信度标注？ | |

工程深度分 = 检查通过数 / 5 × 5
```

二元检查的一致性远高于主观 5 分评分。对于"程度"类标准（如"机理描述的深度"），用字数阈值或结构要求替代主观判断。

**建议 2：增加"评审角色分离"**

```markdown
## 评审执行规则

评审由独立的评审角色执行，与报告生成角色分离：
- 报告生成：research_analyst / finance_analyst / tech_analyst
- 质量评审：quality_reviewer（独立角色，不接触生成过程的上下文）

评审 prompt 中不包含报告生成过程中的推理链或搜索数据，
只包含最终报告文本和分析计划（用于检查结构完整性）。
```

**建议 3：回退指令模板化**

```markdown
## 回退指令格式

对于每个弱项维度，输出结构化的回退指令：

```json
{
  "weak_dimension": "engineering_depth",
  "current_score": 3,
  "target_score": 4,
  "specific_gaps": [
    {
      "section": "6. 失效模式与根因",
      "gap": "IMC 断裂的机理描述缺失",
      "required_action": "补充 Cu6Sn5/Cu3Sn IMC 层的断裂机理，包括：(1) 热应力导致的裂纹扩展方向 (2) Kirkendall空洞对界面强度的影响",
      "required_sources": "至少引用 1 篇 IEEE/ECTC 论文",
      "min_word_count": 200
    }
  ]
}
```
```

**建议 4：增加"相对评分"机制**

不只看绝对分数，还看与同类型历史报告的比较：
```markdown
### 相对质量评估
- 与同类型最近 3 份报告的平均分对比
- 如果当前报告分数 < 历史平均 - 2 分，即使绝对分数 ≥ 24，也标记"质量下降"警告
```

### 2.4 search.md — 搜索策略调整

**评分：3.5/5**

#### 优点
1. **三阶段搜索架构合理**：Breadth-First → Depth-First → Structured Data 的流程设计符合信息检索最佳实践。
2. **Tier 分级体系成熟**：Tier 1/2/3 的来源分级已在实际运行中验证，是可靠的基础。
3. **改进计划中的方向正确**：按研究类型调整搜索策略（技术研究偏学术论文，投资研究偏官方披露）是对症下药。

#### 问题

**P1 — 改进计划中的搜索策略调整细节不足**

IMPROVEMENT_PLAN_v1.md 对 search.md 的改动描述只有：
> `prompts/search.md` | 修改 | 搜索策略按研究类型调整

但没有给出具体的策略差异设计。以下关键问题未回答：

**问题 1：不同研究类型的来源优先级如何不同？**

| 来源 | 技术研究 | 投资研究 | 市场研究 |
|------|---------|---------|---------|
| arxiv.org | Tier 1 | Tier 3 | Tier 3 |
| sec.gov | Tier 3 | Tier 1 | Tier 2 |
| cninfo.com.cn | Tier 3 | Tier 1 | Tier 2 |
| IEEE Xplore | Tier 1 | Tier 3 | Tier 3 |
| Yole/TrendForce | Tier 1 | Tier 2 | Tier 1 |
| 券商研报 | Tier 3 | Tier 1 | Tier 2 |

计划中没有定义这个映射表。

**问题 2：搜索关键词策略如何按类型调整？**

当前 planning.md 的"6 维扩展"策略对所有类型一视同仁。但：
- 技术研究需要：论文关键词（学术术语）、会议名称（ECTC/IMAPS/IEDM）、作者名
- 投资研究需要：股票代码、公告编号、分析师名称
- 市场研究需要：行业报告关键词、市场规模量词（"billion"、"CAGR"）

**问题 3：搜索深度和广度的平衡如何调整？**

- 技术研究：广度低（聚焦学术圈）、深度高（需要精读论文）
- 市场研究：广度高（多源交叉验证）、深度中（摘要级即可）

## 三、Top 3 改进建议（优先级排序）

### 🥇 建议 1：类型识别改用 LLM 语义分类 + 复合类型支持（影响：P0）

**当前问题**：关键词硬匹配无法处理歧义、冲突和跨领域研究。  
**改进方案**：
- 用 LLM 语义理解做分类，关键词列表作为 few-shot hints
- 支持复合类型（`tech_process+investment`）
- 增加 `research_angle` 字段让 LLM 解释分类理由
- 低置信度时触发用户确认

**预期效果**：类型误判率从 ~20% 降至 <5%，跨领域研究不再被迫使用单一框架。

---

### 🥈 建议 2：tech_analysis.md 引入"核心维度 + 可选维度"分层（影响：P0）

**当前问题**：9 维度平铺导致 LLM 认知负荷过高，每个维度深度不足。  
**改进方案**：
- 3 个核心维度（必选）+ 6 个扩展维度（选 3-4 个）
- 总维度数控制在 6-7 个
- Planning 阶段根据 `research_angle` 决定维度选择
- 增加"数据不足"处理指令，防止 LLM 编造数据

**预期效果**：每个维度的分析深度提升 30-50%（token 分配从 ~1K 提升到 ~1.5K per dimension），同时避免"维度填充"。

---

### 🥉 建议 3：质量评审改用"检查清单 + 二元评分"（影响：P1）

**当前问题**：5 分制主观评分的 LLM 执行一致性低（±1 分波动），趋中效应导致"回退-回退-强制通过"的固定模式。  
**改进方案**：
- 将"是否有 X"类标准改为二元检查（有/无）
- 保留少量程度类标准用 3 分制（优/中/差），不用 5 分
- 增加评审角色分离（评审者不接触生成过程上下文）
- 回退指令模板化（具体到章节+缺口+要求动作+字数）

**预期效果**：评分一致性从 ±1 分提升至 ±0.5 分以内，回退次数从"总是 2 次"降至"0-1 次"，报告质量真正由评分驱动而非由 max_retries 驱动。

## 四、其他观察

### 4.1 改进计划中的工程推理层（reasoning.py）与 Prompt 的关系

改进计划中的 `reasoning.py`（改进 #4）是 Python 模块，但其核心功能（5 Whys 因果链、时序推理、失效模式推理）实际上更适合用 prompt 实现（LLM 本身就是推理引擎）。

**建议**：将 `reasoning.py` 的核心逻辑实现为一个 prompt（如 `prompts/engineering_reasoning.md`），而非 Python 代码。Python 代码只负责调用 LLM 并解析输出。这样可以：
- 更容易迭代推理策略（改 prompt 比改 Python 快）
- 利用 LLM 的语义理解能力做因果推理（比规则引擎更灵活）
- 与现有架构一致（其他分析模块都是 prompt-driven）

### 4.2 改进计划的验收标准需要 Prompt 层面的检查项

当前验收标准偏功能层面（"CoWoS-L 报告覆盖全部 9 个维度"），缺少 Prompt 层面的验收：
- [ ] planning.md 输出 `research_type` 字段的 JSON schema 验证通过
- [ ] tech_analysis.md 的维度选择逻辑在 3 个测试用例上正确执行
- [ ] quality_review.md 的评分与人工评分的 Cohen's Kappa ≥ 0.6
- [ ] search.md 按类型调整来源后，Tier 0+1 来源占比提升 ≥ 15%

### 4.3 缺少 Prompt 版本管理策略

所有 prompt 文件当前使用 `version: "1.0.0"` 头部，但改进计划未说明：
- 新 prompt（tech_analysis.md, quality_review.md）的初始版本号
- prompt 迭代的变更管理（谁审批？如何回滚？）
- A/B 测试策略（新旧 prompt 如何对比？）

| **总体** | **3.5/5** | **良好 — 方向正确，核心设计需微调后可执行** |

### 核心结论

改进计划的 **架构设计是正确的**（类型路由 → 专用框架 → 质量闭环），但 **Prompt 层面的执行细节需要加强**。三个最关键的变化：

1. **类型识别**：从"关键词匹配"升级为"LLM 语义分类 + 置信度 + 用户确认"
2. **维度框架**：从"9 维度平铺"升级为"3 核心 + 6 选 4 扩展"分层
3. **质量评审**：从"5 分制主观评分"升级为"检查清单 + 二元评分 + 模板化回退指令"

这三个变化的共同主题是：**降低 LLM 的自由裁量空间，增加结构化约束**。LLM 擅长在明确约束下做深度分析，但不擅长在开放标准下做一致评分。改进计划应该把 LLM 当"执行引擎"而非"判断者"。
