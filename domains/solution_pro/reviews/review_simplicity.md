## 评审：简洁性视角

### 评分：CONDITIONAL

方案方向正确，但存在明显的过度设计。4 个 Fix 中有 2 个可以砍掉或大幅简化。

---

### 逐条分析（5 个问题）

#### 1. 方案是不是过度设计了？

**是的，中度到重度。**

- Fix 1（简化 delivery 逻辑）：**必要**。把分支选择逻辑写清楚、默认走自动路由，这是核心修复。
- Fix 2（pre-flight self-check）：**过度设计**。详见问题 2。
- Fix 3（orchestrator abort 联动）：**解决不存在的问题**。详见问题 3。
- Fix 4（open_id 获取标准化）：**部分必要**。但只需一句话规则："从 feishu.env 读取，禁止猜测"，不需要 4 步 fallback 链。

**可砍掉 Fix 2 和 Fix 3，保留简化后的 Fix 1 + Fix 4。**

#### 2. Pre-flight check（Fix 2）是不是在用一个复杂方案解决一个简单问题？

**是的，严重过度设计。**

问题本质：创建 cron 前确认 channel 和（如果是飞书）open_id。

方案做了什么：
- `exec echo` 打印 channel（多余，Runtime 区域已经写了）
- `exec grep` 读 feishu.env（可以用 `read` 工具一步完成）
- **写入 .cron_preflight.json 文件**（完全没必要——这是给谁看的？下次 cron 创建时会覆盖，不会有人去读这个文件做决策）

**简单方案**：SKILL.md 里写一句话——"创建 cron 前，从 Runtime 读 channel；如果是 feishu，用 `read` 读 feishu.env 获取 open_id。禁止猜测。" 不需要写 JSON 文件，不需要 exec echo。

#### 3. Orchestrator abort 联动（Fix 3）是不是在解决一个不存在的问题？

**是的。**

- Orchestrator abort 是用户主动行为，用户知道自己在干什么。
- Cron 多跑几次 → 检测到没有新阶段 → 无事发生 → 最终超时或被手动清理。
- 方案 A（cron 检测 orchestrator 存活）：增加了一个启发式检测（15 分钟无活动 = 死了？），这会引入误判。如果用户只是暂停了 20 分钟呢？
- 方案 B（主 Agent 兜底清理）：合理但优先级极低，属于 nice-to-have。

**结论**：Fix 3 应该整体降级为 "已知限制，暂不修复"。Cron 超时自清理机制已经够用。

#### 4. 有没有一个更简单的方案？

**有。** 用户自己的洞察就是最好的方案：

> "在哪聊就发哪。"

具体实现：
- SKILL.md Step 4 的 delivery 配置改为：**默认 `{"mode": "announce"}`，不指定 channel/to。**
- 删掉分支 A/B 的选择逻辑。自动路由会处理 95% 的场景。
- 飞书场景作为"已知待支持"单独加一行注释即可。

这样 Fix 1、Fix 2、Fix 4 三个 Fix 全部不需要——因为问题的根源就是"分支选择逻辑太复杂，Agent 执行时搞混了"。删掉分支逻辑 = 删掉出错的可能。

#### 5. 修改文件数量是否反应过度？

**是的。**

- 问题本质：配错了一个参数（channel/to）。
- 方案要改 3 个文件 + 新增 1 个 JSON 文件格式 + 新增 1 个检测逻辑。
- **最小修复**：只改 SKILL.md 一个文件，把 delivery 配置简化为固定默认值。1 个文件，改 5 行。

### 砍掉建议

| Fix | 建议 | 理由 |
|-----|------|------|
| Fix 1 | **保留但简化** | 核心修复，但不需要分支逻辑，直接默认自动路由 |
| Fix 2 | **砍掉** | pre-flight JSON 文件完全没必要，一句话规则足够 |
| Fix 3 | **砍掉** | 解决不存在的问题，超时自清理已够用 |
| Fix 4 | **简化后保留** | 只需"禁止猜测 open_id，从 feishu.env 读取"一句话 |

---

### 最简方案

**SKILL.md Step 4 的 delivery 配置改为固定值 `{"mode": "announce"}`，删掉分支 A/B 选择逻辑，加一句"飞书场景后续支持"。** 改 1 个文件，改 3-5 行。

---

### 最核心的一个建议

**删掉分支逻辑，不要修分支逻辑。** 问题的根源是"分支选择太复杂导致 Agent 执行出错"，解决方案应该是"让分支选择不存在"，而不是"在分支选择前面再加一层检查"。每多一层检查，就多一个出错的机会。
